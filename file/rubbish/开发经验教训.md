# xiaomengresume 开发经验教训

> 本文件记录 xiaomengresume 开发过程中需要遵守的实现层面纪律与陷阱，补充蓝图（`技术栈.md`）与需求清单（`功能需求清单.md`）未展开的细节。
> 按里程碑排列，开始每个阶段前通读对应章节。

---

## 一、M0 骨架阶段（立项目即生效）

### 0.1 环境洁癖：第一天就做对

**教训**：混合包管理器（pnpm/npm/yarn 混用）会导致 node_modules 多套目录混战，排查根因耗时。

**操作**：
- 单一 pnpm，不用 npm/yarn，混用即自残
- `package.json` 设 `"packageManager": "pnpm@<version>"`
- `.gitignore` 第一天就覆盖：`.npmcache/`、`*.log`、`dist/`、`electron-dist/`、`out/`
- 拒绝 `npx -y` 运行时下载工具链——pnpm 全局可用即可
- 所有 CLI 命令用绝对路径或 `pnpm run`，不依赖隐式 cwd

### 0.2 主进程构建管线：M0 第一天就验证，不能拖

**教训**：Vite 只覆盖渲染进程，主进程 TypeScript 编译要另起炉灶；若拖延到后期才发现拼不起来，返工极大。

**操作**：
- M0 第一件事：跑通 `Electron + Vite(渲染进程) + TypeScript(主进程)` 的完整 dev/build 循环
- `vite-plugin-electron` 或 `electron-vite` 二选一，在 `package.json` 脚本里定死
- 验证 target：主进程 `"type": "module"` + AI SDK v7（ESM-only）能正常 `import`，不报 CJS/ESM 混用错误
- 可验证产出：`pnpm dev` 打开 Electron 窗口；`pnpm build` 产出可运行的 asar

### 0.3 printToPDF 时序陷阱：等 fonts.ready

**教训**：`webContents.printToPDF()` 若在字体/CSS 未就绪时调用，产出 PDF 中文乱码/排版错位。

**操作**：
```ts
// 主进程 printToPDF handler 必须等：
await win.webContents.executeJavaScript('document.fonts.ready')
// 然后才调用：
const pdf = await win.webContents.printToPDF({
  preferCSSPageSize: true,
  printBackground: true,
})
```
- M0 用一份最简单的 HTML（含中文字体引用，如思源黑体/系统字体）验证 end-to-end：加载 → fonts ready → printToPDF → 文件落盘且中文不乱码

### 0.4 AI SDK 主进程验证：它不是"服务器"

**教训**：Electron 主进程是 Node.js 但不是 HTTP 服务器，不存在 request context / proxy 层；不能复用依赖服务端上下文的 AI 调用写法。

**操作**：
- M0 在 Electron 主进程中 import AI SDK，跑一次 `streamText({ prompt: "hello" })`，验证：
  - (a) ESM import 不报错
  - (b) API Key 从 safeStorage/electron-store 读出后能正常传入 SDK
  - (c) 流式 chunk 能经 `webContents.send()` 推到渲染进程
- 这一步暴露所有"把主进程当服务器用"的幻觉，比后续返工便宜

### 0.5 i18n 脚手架前移到 M0

**教训**：若前期硬编码中文字符串散落各处，后期想支持英文时需要 grep 数百个文件改一遍。

**操作**：
- M0 立即建 `src/renderer/i18n/`，`zh-CN.json` / `en.json` 两个空对象即可
- `react-i18next` 初始化，挂 `<I18nextProvider>`
- **铁律**：任何 UI 文案从第一行代码起就走 `t('key')`，哪怕 key 是临时的
- 先只用 `zh-CN.json` 写内容，`en.json` 留空或机器翻译标记——但**结构必须对称**
- Vite 配 `@intlify/unplugin-vue-i18n` 之类的按需加载（可选，看要不要 split chunks）

## 二、M1 编辑器阶段

### 1.1 高亮隔离：class 作用域铁律

**教训**：高亮清除若不限定 className，会误清其他功能的高亮——修起来一行代码，但暴露的是「没有全局约定、新功能不做隔离测试」的工程纪律问题。

**操作**：
- 在 M1 建立第一条标记功能时，就在 `src/shared/constants.ts` 统一定义所有高亮 class 名：
  ```ts
  export const HIGHLIGHT = {
    GRAMMAR_ERROR: 'grammar-error',
    MATCH_FOUND: 'match-found',
    // 未来新增功能在此追加
  } as const
  ```
- 所有标记/清除函数强制：
  ```ts
  // ✅ 正确
  mark(keyword, { className: HIGHLIGHT.MATCH_FOUND })
  unmark({ className: HIGHLIGHT.MATCH_FOUND })

  // ❌ 禁止——任何 PR review 看到无参 unmark() 直接拒绝
  unmark()
  ```
- **不是建议，是铁律**。违例 = 等着被其他功能的高亮互相覆盖。

### 1.2 撤销/重做与 Tiptap 自己的 undo 不打架

**教训**：全局 undo 不能跟 Tiptap 内部 undo 抢键盘事件。

**操作**：
- 全局 Ctrl+Z / Ctrl+Y 只触发**提交级**变更（失焦、回车、点工具栏按钮等）
- 用户在 Tiptap 内部打字时不入全局栈——Tiptap 自己的 `history` 扩展处理
- 富文本字段失焦时，把 Tiptap JSON 内容序列化入全局栈（算一次"提交"）
- 防抖合并：连续失焦/输入在 500ms 内的变更合并为一步

### 1.3 Zod schema 版本化从第一天开始

**教训**：若等到想改 schema 时才发现旧简历文件打不开，就回不去了。

**操作**：
- `ResumeSchema` 第一条字段：`schemaVersion: z.literal(1)`
- M1 就写好迁移骨架：
  ```ts
  function migrate(data: unknown): ResumeData {
    switch (data.schemaVersion) {
      case 1: return ResumeSchema.parse(data) // 当前版本，空迁移
      default: throw new Error(`Unsupported schema version: ${data.schemaVersion}`)
    }
  }
  ```
- 以后每次改 schema → 升 `schemaVersion` → 加 case

## 三、M2 模板与导出阶段

### 3.1 "模板 = 打印"的正确理解

**教训**：不能把 Tiptap 的 `contenteditable` DOM 直接喂给 `printToPDF`。

**操作**：
- **单一事实源 = Zod 数据模型**，不是一份 DOM
- 编辑态：Tiptap 控件消费数据模型 → 用户编辑 → 写回数据模型
- 打印态：React 模板组件消费数据模型 → 渲染干净 HTML → `printToPDF`
- 两条渲染路径共享数据模型 + CSS 变量主题，但 **DOM 完全不同**

### 3.2 CSS @page 分页验证趁早

**教训**：`@page` 在三端 Chromium 的行为有细微差异（尤其 `page-break-inside: avoid` 在中文字段跨页时）。

**操作**：
- M2 一旦有第一套可用模板，立即用 A4 尺寸跑三端 `printToPDF` 验证：
  - `@page { size: A4; margin: 15mm; }` 三端一致
  - `page-break-inside: avoid` 在中文字段跨页时生效（不硬截断一行文字）
  - `page-break-before: always` 在章节间正确分页
- 如果发现某个平台行为异常 → 记录到模板 README 的 known issues

## 四、M3 AI 功能阶段

### 4.1 薄封装，拒绝厚抽象

**教训**：在已返回标准结构的调用外再包一层 parser，是"没读现有代码就设计"——造了轮子套轮子。

**操作**：
- 每条 AI 能力 = 一个 IPC handler，直接调 `streamText` / `generateObject`
- **不要**在 AI SDK 外面再包一个"我们的 AI 服务层"——SDK 本身就是抽象
- 等 3 条 AI 功能都写完后（润色 + 语法 + 匹配度打分），如果发现有 **3 处以上** 完全相同的样板代码，再抽共享函数——**不要提前抽象**
- 代码 review 时灵魂拷问：这层抽象是因为"这里有重复"还是因为"我觉得以后会重复"？→ 前者允许，后者砍掉

### 4.2 AI SDK v7 的 API 陷阱

**教训**：易下意识写旧 API（`system`→`instructions`、`fullStream`→`stream`）。

**操作**：
- M3 开始前，先建一个 `src/main/ai/sdk-helpers.ts`：
  ```ts
  // 集中导入 AI SDK，统一正确的 API 用法
  import { streamText, generateObject } from 'ai'
  import { createOpenAI } from '@ai-sdk/openai'
  // ...
  export { streamText, generateObject, createOpenAI }
  ```
- 所有 AI handler **只从这个文件 import**，避免各文件散落不同版本的 SDK 调用
- 豆包用 `createOpenAI({ baseURL: userEndpoint })`——AI SDK 不区分"真 OpenAI"和"兼容 OpenAI"，一行接入

### 4.3 视觉模型双向守卫

**教训**：视觉导入请求落到不支持视觉的模型时，若报错只是底层 `fetch failed` 而非明确提示，用户无法理解。

**操作**：
- 主进程 IPC handler：收到 vision 请求 → 检查当前模型 → 不支持直接 `throw new Error('VISUAL_NOT_SUPPORTED')`
- 渲染进程捕获该错误 → 显示"当前模型不支持图片/PDF 识别，请切换至 Gemini / GPT-4o / 豆包视觉版"
- 设置页面在模型选择器里为视觉模型加 tag：`✓ 支持图片/PDF 导入`
- 非视觉模型的"导入 PDF"按钮置灰 + tooltip 解释原因

## 五、M4 导入阶段

### 5.1 三步核对流不可跳过

**教训**：这不是 UX 优化，是**数据完整性底线**。

**操作**：
- ① AI 首轮映射 → ② 并排预览（左侧原始文本 / 右侧结构化结果） → ③ 用户逐段核对/修改 → ④ 确认写入
- 面对双栏/表格 PDF 时 AI 准确度可能降到 50% 以下——若跳过核对，用户等于导入了一份"随机简历"
- UI 上**不提供"一键导入"按钮**——每一条经验/教育/项目都必须经过用户视线

## 六、M5 打包阶段

### 6.1 electron-builder 的 Defender 锁

**教训**：Windows Defender 实时扫描可能在 electron-builder 打包时锁 `.exe` / `asar`，导致打包卡死，与是否精简依赖无关。

**操作**：
- M5 首次打包前：把项目目录加入 Defender 排除列表，或临时暂停实时扫描
- 如果打包卡在 `packing` 阶段超过 5 分钟 → 99% 是 Defender → 不要怀疑代码
- 参照 `electron-builder-portable` 技能经验（已有 skill，M5 时直接加载）

### 6.2 safeStorage 的 Linux 降级

**教训**：缺系统密钥环的 Linux 上 `isEncryptionAvailable()` 为 false，需定义降级 UX。

**操作**（M5 时决定二选一）：
- **方案 A（推荐）**：降级存 Key
  - `safeStorage.isEncryptionAvailable()` 为 false 时 → 退用 electron-store 存 Key
  - 弹一次性警告："当前系统不支持硬件级加密，API 密钥将以弱加密存储。建议在支持密钥环的系统中使用。"
  - 不阻塞用户使用
- **方案 B（更安全）**：拒绝存 Key
  - safeStorage 不可用 → 拒绝保存 → 每次启动手动输入 Key
  - 体验差但最安全

### 6.3 electron-updater 的"离线"矛盾（已定案）

**教训**：自动更新需要托管更新清单（GitHub Releases 或静态端点），曾与"离线/无服务器"定位打架。

**决策（2026-08-05）**：**采用 electron-updater + GitHub Releases 更新源**。
- 开源免费定位下 GitHub 即免费静态托管（latest.yml + 安装包），零成本。
- 应用**仅在启动时静默检查一次**（或设置页手动点「检查更新」）才联网；编辑/导出/存储全流程仍完全离线。
- 体验对齐主流桌面应用：有新版本弹提示 → 下载 → 重启安装；失败静默，不影响使用。
- 不要在设置页写"离线"字样暗示永不更新——README 信任承诺里注明"仅检查更新时联网"。

## 七、全阶段通用教训

### G.1 先读文档再写代码

**教训**：轮子套轮子、花哨抽象的共同根因——动手前没把蓝图/需求清单/已有代码读透。

**操作**：
- 每开始一个新功能，先回答三个问题：
  1. 蓝图里有没有相关约束？（比如淘汰了 Paged.js → 别又引进来）
  2. 需求清单里有没有已定义的数据流？（比如 AI 必须走 IPC → 别写成直连）
  3. 现有代码里有没有可复用的？
- 对 clean-room 项目这尤其重要——没有遗留代码可依赖

### G.2 依赖引入前自问三题

**教训**：puppeteer（下载 Chromium）、sharp（原生编译）、better-sqlite3（原生编译）——这些依赖一旦引入，打包/安装/跨平台都会多一个可能炸的点。

**操作**，每引入一个新依赖，自问：
1. 需要原生编译吗？→ 高风险，必须有充分理由
2. 会下载额外二进制吗？→ 高风险，必须有离线缓存方案
3. npm 上次发版超过 2 年了吗？→ 中风险，项目可能已弃坑

### G.3 沙箱协作模式

**教训**：沙箱 git 不可用、vite build 的 safe-delete 假报错、Bash cwd 偏差——这些是**环境特性而非应用 bug**，排查是浪费时间。

**操作**：
- Agent：编辑文件、跑类型检查、跑模块 transform、写文档/报告
- 用户本机：git 提交/分支/合并、完整构建、打包、端到端测试
- 所有路径用绝对路径（`E:\ai\aiwork\shixi\xiaomengresume\src\...`），不依赖 cwd
- 如果沙箱里报错而用户本机正常 → 不予处理，记录为"沙箱环境假阳性"

### G.4 渐进复杂度：先跑通再优化

**教训**：模型分配矩阵、多层 AI 服务抽象——都是"还没跑通就搞了花哨设计"。

**操作**：
- 每条功能先写最简版本（硬编码一个模型、一个 prompt、一个返回格式）→ 端到端跑通
- 跑通后再加：模型选择器、prompt 模板、错误重试、流式优化
- 永远不要**同时**写"功能实现"和"架构抽象"——前者验证想法，后者固化模式

### G.5 开源项目纪律（定位升级新增，2026-08-05）

**教训**：调研显示付费墙/订阅是简历工具最大差评源；开源免费 + 隐私 + 防盲信是差异化护城河。但开源项目一旦"门面"（README/CI/Issue 处理）失守，信任承诺就崩塌。

**操作**：
- **信任承诺写进 README 首屏**：真正免费（无水印/无付费墙/不阉割）· 数据主权（本地存储/代码可审计/BYOK）· 人工掌控（AI 辅助非替代）。任何界面文案不得与这三条矛盾——**禁止任何"付费解锁/水印/限次数"字样**。
- **M0 第一天建 CI**（lint/typecheck/test/build），个人项目靠自动化兜住回归。
- **Issue/PR 模板 + Discussions**：第一个 issue 出现前就建好，避免协作规则临时拍脑袋。
- **隐私打码模式（F16）是低成本高价值的信任功能**：截图求点评、发社区不再需要手动 P 图——上线前必须有。
- **发布即门面**：GitHub Releases 带 changelog + 三端产物 + 校验和；README 截图用真实界面（脱敏后）。
- **安全披露路径**：SECURITY.md 声明 API Key 使用 `safeStorage` 加密、无任何遥测/数据上报——用户能审计，就是最大的信任。
