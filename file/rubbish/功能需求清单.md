## 〇、全局约定（所有功能必须遵守）

1. **架构铁律**
   - 主进程（Node.js）统一承载 **AI / 文件 / 打印 / 加密**；渲染进程纯 UI，API Key 永不落前端，天然无 CORS。
   - 所有 AI 调用经 **IPC → 主进程 → Vercel AI SDK（BYOK）**，渲染进程不直接连供应商。
   - **Zod 简历数据模型为唯一事实源**；编辑态与打印态共享数据模型 + CSS 主题变量（"模板 = 打印"）。
2. **编辑范式（P0 已定案 = 混合；三选项对比见 F2）**
   - 结构化字段（姓名/公司/日期/学校/技能等）→ 受控表单组件。
   - 富文本字段（自我评价、每条工作/项目的 bullet 描述）→ **Tiptap 仅作富文本输入控件**，不做整页文档。
   - 预览/打印 → React 模板组件消费数据模型 + CSS `@page`。
3. **目录约定**（详见技术栈蓝图）
   - `src/shared/`：Zod schema、IPC 契约、类型（主/渲染进程共享）。
   - `src/main/`：Electron 主进程（AI / 文件 / 打印 / 加密 / IPC handlers）。
   - `src/renderer/`：React SPA（编辑器 / 预览 / 设置 / 导入向导）。

## 二、功能详细需求与实现框架

### F1 · 简历数据模型（地基）
- **需求**：定义中英结构化简历，支持版本化 JSON 持久化与向后迁移。
- **实现框架**：
  - `src/shared/schema/resume.ts`：用 Zod 定义 `ResumeSchema`，section 含 `basics / education / work / projects / skills / certificates / languages / summary`。
  - 富文本字段用 `RichText` 类型（`{ type: 'doc', content: [...] }` Tiptap JSON，或降级 HTML 字符串）。
  - 每条目带稳定 `id`（uuid）以支持增删与撤销。
  - 版本号 `schemaVersion` 字段；导入旧数据走迁移函数。
- **技术栈对应**：Zod（单一事实源）、版本化 JSON、uuid。

### F2 · 编辑器（混合范式）
- **需求**：可编辑一份完整结构化简历，所见即所得地预览。
- **实现框架**：
  - `EditorPane`：左/上表单区，结构化字段用 shadcn `Input/Textarea/DatePicker/Select`；富文本字段嵌入 `<TiptapField>` 控件（仅 description/summary）。
  - `PreviewPane`：右/下 React 模板组件实时消费 store 中的 `ResumeSchema`。
  - 共享 `useResumeStore`（Zustand）持有当前简历；编辑即改 store，预览即读 store。
- **技术栈对应**：React 18/19 + shadcn/ui (Radix) + Tiptap v3（MIT 扩展）+ Zustand + lucide-react。
- **注意**：编辑态 DOM ≠ 打印态 DOM，二者通过数据模型解耦。

#### P0 编辑范式三选项对比（定案 = 混合）

编辑范式是牵动编辑器、导出一致性、AI 导入、撤销栈一整条链路的**根决策**。三种候选及其取舍如下：

| 维度 | ① 混合（**已定案选中**） | ② 纯 WYSIWYG | ③ 纯表单 |
|---|---|---|---|
| **长相** | 左/上表单卡片 + 右/下实时模板预览 | 单页可编辑画布，直接拖拽/改样式，所见即所得 | 纯表单卡片录入，预览分离（或无即时预览） |
| **技术路径** | 受控表单（shadcn）+ Tiptap 富文本控件（仅 description/summary）+ React 模板组件消费 store | `contenteditable` / Tiptap 整页文档 / 类 Notion 块编辑器 | 仅受控表单，无富文本控件、无同屏预览 |
| **导出一致性（F5）** | **强**：预览与打印同源（模板=打印），矢量、文字可选 | **弱**：编辑态=打印态难保证，双栏/表格/艺术字易破坏矢量导出 | **强**但用户无即时反馈 |
| **ATS 友好（设计保证）** | 内置模板默认单栏/标准标题/系统字体/文字可选，天然 ATS 友好 | 风险高：自由排版易出双栏/图片化文本，ATS 漏读（竞品已验证最高 30%） | 强：结构化数据天然 ATS 友好 |
| **AI 导入（F6/F10）** | **天然有字段可填**，三步核对直接映射 | 需从可视化 DOM **反向解析**成结构化数据，成本高、易错 | 直接填字段，但无预览难判断导入效果 |
| **撤销（F3）** | 表单快照（Zustand 历史栈）+ 富文本内 undo，分工清晰 | 整页 undo 复杂，光标/选区状态难管理 | 简单（表单级快照即可） |
| **工作量** | 中 | **高**（画布引擎/约束求解/响应式分页） | 低 |
| **结论** | ✅ 采用 | ❌ 拒绝 | ⚠ 备选（极致稳妥但体验差） |

**为何选混合、拒纯 WYSIWYG：**
- 纯 WYSIWYG 的核心矛盾是**「编辑态」与「打印态」同源难保证**——你能在画布上拖出花，但导出 PDF 时字体/分页/矢量保真全要重新迁就，且双栏、表格、艺术字直接踩矢量导出（F5）与 ATS 兼容的雷。
- 更致命的是它让 **F6/F10 三步核对成本陡增**：AI 导入后需要把可视化 DOM 反向拆回结构化字段，等于多一道易错的解析层。混合范式下数据本就是结构化的，导入即填字段。

**为何不选纯表单：**
- 纯表单技术上最稳、最省，但**缺「所见即所得」反馈**——用户填完不知道最终长什么样，投递前焦虑，且弱化了「模板/主题切换」的直观价值（F4）。
- 简历场景用户普遍期待实时预览，纯表单体验降级明显。

**混合的代价（已知、可接受）：** 自由美术排版能力弱（L4 拖拽不做）；但简历本质是结构化数据，本来不需要自由画布——这正是「模板=打印」铁律能成立的前提。

### F3 · 撤销 / 重做
- **需求**：编辑过程可 Ctrl+Z / Ctrl+Y，防止误操作。
- **实现框架**：
  - `src/renderer/store/history.ts`：自维护轻量历史栈，对 `ResumeSchema` 做结构化克隆快照（上限 50 步）。
  - 每次"提交级"变更（失焦/回车/按钮）入栈，连续输入防抖合并。
  - 快捷键绑定 + 工具栏按钮；与 Tiptap 内部 undo 区分（富文本框内用 Tiptap 自身 undo，提交后并入全局栈）。
- **技术栈对应**：Zustand + 自维护栈（**不引入 zundo**，见蓝图 ADL）。

### F4 · 模板系统 + 主题
- **需求**：多套简历模板可切换，主题（配色/字体/间距）可换。
- **实现框架**：
  - `src/renderer/templates/`：每套模板 = 一个 React 组件，props 为 `ResumeSchema`。
  - `src/renderer/templates/registry.ts`：模板注册表（id → 组件 + 缩略图）。
  - 主题用 **CSS 变量**（`--resume-font / --resume-accent / --resume-spacing`），`ThemeProvider` 切换变量，零组件重复。
  - 分页用 CSS `@page` + `page-break-*` / `break-inside: avoid`。
- **技术栈对应**：React 组件 + CSS 变量 + Tailwind v3/v4（**不引入 Paged.js**，见蓝图 ADL）。

### F5 · PDF 导出（矢量）
- **需求**：一键导出高保真、文字可选、体积小的矢量 PDF。
- **实现框架**：
  - 渲染进程 `ipcRenderer.invoke('pdf:export', { templateId, theme })`。
  - 主进程：将选定模板 + 当前数据渲染为 HTML（复用 `PreviewPane` 同款组件/SSR 字符串），载入隐藏 `BrowserWindow` 或复用渲染进程 `webContents`。
  - **等 `document.fonts.ready`** 后再 `webContents.printToPDF({ preferCSSPageSize: true, printBackground: true })`。
  - 通过 `dialog.showSaveDialog` 落盘。
- **技术栈对应**：Electron `webContents.printToPDF` + CSS `@page`（**替代 html2canvas 栅格化**，见蓝图 ADL）。

### F6 · PDF 导入 + AI 映射（三步核对）
- **需求**：导入已有 PDF 简历，映射成本地数据模型，且不准许"盲信 AI"。
- **实现框架**：
  - `ipcRenderer.invoke('pdf:import', { filePath })` → 主进程 `unpdf.extractText(buffer)` 抽文本。
  - 主进程 `generateObject({ schema: ResumeSchema, ... })` 做首轮映射。
  - 渲染进程 **三步向导**：① 展示 AI 映射结果预览 → ② 用户逐段核对/手改 → ③ 确认写入 store。
  - 双栏/表格/不规则排版时 AI 不可 100% 依赖，向导不可跳过。
- **技术栈对应**：unpdf（Node 原生、含 CMap 中文）+ Vercel AI SDK `generateObject` + Zod 边界校验。

### F7 · AI 润色（辅助定位）
- **需求**：选中文本/字段，AI 改写为更专业/简洁的表达，流式返回。**定位为辅助编辑——用户掌控最终内容，不做整篇自动生成。**
- **实现框架**：
  - 渲染进程选中 → `ipcRenderer.invoke('ai:polish', { text, field })`。
  - 主进程 `streamText({ model, instructions: <润色角色提示>, prompt: text })`（`instructions` 替代旧 `system`，见 v7 破坏性变更）。
  - 流式 chunk 经 `webContents.send('ai:polish:chunk', ...)` 推回 → 渲染进程实时写入 Tiptap/字段。
  - 提供"接受/放弃"对比。
- **技术栈对应**：Vercel AI SDK v7 `streamText` + 主进程 + 类型化 IPC。

### F8 · AI 语法检查
- **需求**：检查语法/拼写/表达问题，原位标记并给建议。
- **实现框架**：
  - `ipcRenderer.invoke('ai:grammar', { text })` → 主进程检测，返回 `{ from, to, message, suggestion }[]`。
  - 渲染进程用 **class 作用域**标记（如 `.grammar-error`），清理时用 `unmark({ className: 'grammar-error' })`，避免误清其他高亮（如匹配度 `.match-found`）。
  - 点击标记展示建议，一键替换。
- **技术栈对应**：AI SDK + Tiptap 标记 API（class 作用域）。

### F9 · 岗位匹配度打分
- **需求**：简历 vs 岗位 JD 给综合分 + 维度分 + 改进建议。
- **实现框架**：
  - 数据模型增可选 `targetJobDescription` 字段（仅增不改）。
  - `ipcRenderer.invoke('ai:match', { resume, jd })` → 主进程 `generateObject({ schema: MatchScoreSchema })` 返回 `{ overall, dimensions[], suggestions[] }`。
  - 渲染进程用卡片/进度条展示，建议可一键"去润色"。
- **技术栈对应**：AI SDK `generateObject` + Zod（`MatchScoreSchema`）。

### F10 · AI vision 导入（图片 / 扫描件）
- **需求**：从图片或扫描版 PDF 用多模态模型抽取结构化简历。
- **实现框架**：
  - 复用 F6 三步向导；输入为图片/base64 或扫描 PDF。
  - 主进程统一 `callAIVision`（Gemini `inlineData` / OpenAI·豆包 `image_url` content 数组分支），返回文本后走 F6 的 `generateObject` 映射。
  - **服务端守卫**：非视觉模型（如 deepseek）直接 400 拒绝；客户端在选型时禁用不支持视觉的模型。
- **技术栈对应**：AI SDK 多模态 + 视觉模型（仅 gemini/openai/doubao 支持）+ 双向守卫。

### F11 · 持久化与设置
- **需求**：本地保存多份简历 + 应用设置，可备份、可副本。
- **实现框架**：
  - 简历数据 → `userData/resumes/<id>.json`（版本化），支持新建/重命名/复制/删除。
  - 应用设置（语言、默认模板、主题、更新偏好）→ `electron-store`（v11，ESM）。
  - 自动保存防抖；启动时恢复上次编辑的简历。
- **技术栈对应**：electron-store（设置）+ `fs` userData（简历，JSON 够用，**不引入 better-sqlite3**，见蓝图 ADL）。

### F12 · API Key 管理（BYOK）
- **需求**：用户填写自带的供应商 API Key，加密存本地，运行时解密使用。
- **实现框架**：
  - 设置界面输入 Key + 选择模型/endpoint（豆包走 `createOpenAI({ baseURL })`）。
  - 主进程 `safeStorage.encryptString(key)` 落盘；读取 `decryptString`。
  - **降级**：`safeStorage.isEncryptionAvailable()` 为 false（缺系统密钥环的 Linux）时，退回 electron-store 弱加密并弹告警。
- **技术栈对应**：Electron `safeStorage`（**不用 electron-store 的 encryptionKey**，其明确标注非安全用途）。

### F13 · 国际化（zh / en）
- **需求**：中英双语界面，随系统或手动切换。
- **实现框架**：
  - **M0 即立脚手架**：`i18n` 初始化 + `zh-CN.json` / `en.json` 空壳。
  - 所有界面文案走 `t('key')`，**禁止硬编码中文字符串**（避免 M5 返工）。
  - 简历模板内的示例文案也按语言走。
- **技术栈对应**：react-i18next + i18next。

### F14 · 自动更新（可选）
- **需求**：新版本发布时提示/静默更新。
- **实现框架**：
  - `electron-updater` 监听更新；需托管更新清单（GitHub Releases 或静态 JSON 端点）。
  - **与"离线/无服务器"定位冲突**：要么接受最小静态托管，要么从离线定位移除自动更新（二选一，见蓝图风险章节）。
- **技术栈对应**：electron-updater。

### F15 · 打包分发 + 开源发布
- **需求**：离线 exe / dmg / AppImage，含免安装便携 zip；开源项目以 GitHub Releases 发布。
- **实现框架**：
  - `electron-builder` 配置；`node_modules` 外部化；处理 asar / Windows Defender 锁。
  - `electron-builder-portable` 技能经验复用（SSR 桌面打包坑点规避）。
  - 三端各验一次 `pageSize` 行为差异（以 A4 默认）。
  - **发布流水线**：GitHub Actions 打 tag → 构建三端产物 → 自动上传 GitHub Releases；`electron-updater` 以 Releases 为更新源（仅启动时静默检查，核心功能完全离线）。
- **技术栈对应**：electron-builder + electron-updater + GitHub Actions + GitHub Releases。

### F16 · 隐私打码模式（调研新增）
- **需求**：一键遮蔽姓名 / 电话 / 邮箱等敏感字段，便于截图发社区求点评、或导出"脱敏预览版"，杜绝隐私裸奔（OpResume 已验证该需求）。
- **实现框架**：
  - 渲染进程顶栏「👁 隐私模式」开关；开启时对 basics 敏感字段（name/phone/email/address）做 CSS 遮蔽（如 `████` 占位 + `filter: blur`）。
  - 遮蔽逻辑作用于**打印态模板**，因此「隐私模式下导出的 PDF」自动脱敏；编辑态表单不受影响。
  - 快捷键 `Ctrl+Shift+P` 快速切换；状态栏常驻提示「隐私模式已开启」。
- **技术栈对应**：CSS 脱敏 + 主题变量（复用 F4 打印态渲染路径），无新依赖。
- **注意**：脱敏仅针对模板渲染层，Zod 数据模型不变——避免两份数据源。

### ATS 兼容（设计保证，不再单独提示）
- **决策**：不再设置独立的 ATS 检查界面 / 角标 / 导出卡片（原 F17 已移除）。所有内置模板**默认兼容 ATS**——单栏布局、标准 section 标题、系统字体或内嵌 OFL 矢量字体、文字可选中；矢量导出天然契合 ATS 与企业投递系统读取。
- **理由**：ATS 被筛的核心风险来自"非标准 / 图片化 / 双栏"版式。本项目"模板 = 打印"架构 + 内置模板库从设计上规避了这些风险，无需再对每个模板打兼容性标记或弹检查清单。
