## 三、可行性评估

### 3.1 技术可行性 —— ✅ 高

- 所有选型均为成熟生态，无冷门/停维依赖（已淘汰项都有替代）。
- 唯一硬约束（AI SDK v7 要求 Node 22+ / ESM-only）已被 Electron 43 内置 Node 24 满足。
- 主进程 / 渲染进程边界清晰（AI/文件/打印/加密在主进程，渲染纯 UI），规避 CORS 与 Key 泄露。
- 「模板 = 打印」通过共享 Zod 数据模型 + CSS 变量实现，架构上自洽。
- **技术风险几乎全部集中在「工程落地」而非「选型」**：主进程构建管线未定、ESM/CJS 混用、@page 三端差异——这些是可解的工程问题，不是死结。

### 3.2 产品可行性 —— 🟡 中高

**差异化优势（真实存在）**：
- 离线 + 本机数据：切中「简历数据敏感、不想上传云端」的用户；
- BYOK：零服务器成本，AI 功能对个人开发者可负担；
- 三步核对导入：竞品（如各类在线简历工具）普遍"一键导入"，本项目把"防盲信 AI"做成信任点，产品理念独特。

**结构性风险（必须正视）**：
- **免费竞品密集**：在线简历工具（FlowCV / 超级简历 / 简历本等）普遍免费或低价，且 AI 功能已普及。离线单机形态的付费意愿存疑。
- **商业化路径未定**：MIT 还是闭源？收费还是免费？文档 P1 至今未决，直接影响整个开发投入的回报预期。
- **BYOK 的双刃剑**：降低产品门槛，但用户要先有 Key 才能体验 AI 亮点——冷启动体验有摩擦。
- **无竞品对标/用户验证**：目前全部分析是"自认为的需求"，未做过任何目标用户访谈或竞品研究。

### 3.3 交付可行性 —— 🟡 中（范围偏大）

- 15 个功能 × 5 个里程碑，对个人/小团队是 2–3 个月的持续投入。
- 建议 **MVP 收窄**：F1–F5 + F11 + F13 是"编辑器 + 导出"闭环，足以形成可用产品；F6–F10 的 AI 导入与润色可作为 v1.1 增量。理由：AI 功能依赖 BYOK 且调试成本高，放到核心闭环稳定之后再上，风险更低、反馈更快。
- M0 的「主进程 ESM 构建管线」是首个技术门槛，建议第一天就验证（经验教训 0.2 已强调）。

## 五、优化空间（按优先级）

### 5.1 P0 —— 开工前必须定（3 天内）

**① 编辑范式决策矩阵**

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **混合（默认）** | 排版稳定、PDF 干净、导入有处安放 | 自由排版弱 | 简历类结构化场景 ✅ **推荐** |
| 纯 WYSIWYG | 所见即所得直觉强 | PDF 分页脏、导入映射难 | 文档类 |
| 纯表单 | 最稳 | 富文本表达受限 | 极简工具 |

> 建议：**维持混合范式**，它已被 3 份文档论证且 UI 原型按此绘制。既然文档已默认混合，就把它从"待确认"改为"已确认"，解除全项目最大不确定性。

**② 主进程构建管线**：推荐 **electron-vite**（一体化解法，主/预加载/渲染三端配置成熟，与蓝图"Vite 纯 SPA"不冲突，electron-vite 底层就是 Vite）。备选 vite-plugin-electron。M0 第一天用「一份含中文字体的 HTML → printToPDF 成功」作为验收。

**③ MVP 范围收窄**：
- **v1.0 = M0–M2 + F11 + F13**（骨架 → 编辑器 → 模板导出 → 持久化 → i18n），交付"能编辑、能导出、数据不丢"的完整闭环。
- **v1.1 = M3**（润色 / 语法 / 匹配度），**v1.2 = M4**（导入 / 视觉）。
- 收益：2–3 个月压到 1–1.5 个月出可用版本，先验证产品假设，再投入 AI 复杂度。

**④ electron-updater 去留**：选 **B（彻底离线）**——砍掉依赖，设置页放"检查更新"按钮手动触发 GitHub API 查询。与离线定位完全自洽，省一个静态托管。

### 5.2 P1 —— M0 期间顺手定

**⑤ 中文字体策略**：打包内置字体（如思源黑体子集化）会显著增大安装包；建议 **v1.0 用系统字体 + 明确 fallback 链**（`"PingFang SC","Microsoft YaHei","Noto Sans CJK SC",sans-serif`），把「内嵌字体」列为可选功能或 v2.0。printToPDF 中文字体需在 M0 实测（经验教训 0.3 已列）。

**⑥ 数据安全三件套**（补进 F11）：
- 自动保存（已有）+ **崩溃恢复**：启动时检测上次未正常退出的临时文件；
- **自动备份**：每份简历保留最近 N 份 `.bak`；
- 设置页提供「导出全部数据为 zip」一键备份。

**⑦ 本地日志与诊断**：主进程写 `userData/logs/app.log`（滚动 5MB），设置页「关于」里放「导出日志」按钮——离线应用没有云上报，这是唯一的排障通道。

**⑧ 版本定案**：React 19、Tailwind v4、Zustand 5（蓝图已建议）、Zod 用 `zod/v4` 子路径（AI SDK v7 peer 要求）。

**⑨ 依赖缓存更新策略**：`deps-cache-reusable.tar.gz` 基于旧 `shixi/` 目录生成，与最终 package.json 有偏差。建议 M0 定稿 package.json 后**重新生成一次**缓存并删除旧包，避免"缓存误导"（旧 tar.gz 44MB 里一半是版本不符的包）。

### 5.3 P2 —— 随里程碑推进

**⑩ 竞品对标与验证**：上线前做一次 10 分钟快速扫描（FlowCV / 超级简历 / Teal / Rezi 等），提炼 3 条差异化主张写进产品页/关于页——当前"自认为的需求"需要外部证据。

**⑪ 首启体验优化**：随应用分发 1–2 份**示例简历**（中英各一），首启即能演示模板切换与导出——降低第一印象门槛（欢迎界面原型已具备基础）。

**⑫ 模板生态化**：模板注册表（registry.ts）预留「模板包导入」能力（JSON 定义 + 缩略图），v1.0 先内置 3 套，社区模板包作为 v2 扩展点——这是低成本高增值的方向。

**⑭ 版本控制纪律**：`git init` 在 M0 第一天做；log.md 的"唯一归口"规范建议同步到 CONTRIBUTING 或 README，防止新人（或未来的自己）违反。

### 5.4 内嵌字体技术可行性（2026-08-05 评估）

> 解析待拍板 #7「中文字体策略」与 §4 风险 #5。字体由 F4 主题 `--resume-font` CSS 变量控制，导出走 Electron `webContents.printToPDF()`（F5），"模板=打印"铁律保证预览即导出。

**可行性判定：✅ 完全可行，且成本极低。**

关键机制：`printToPDF()` 底层是 Chromium 打印管线，会在生成 PDF 时**自动把文档实际用到的字形子集化并嵌入（subset embedding）**。因此"编辑器用某字体"与"PDF 嵌入该字体"是同一件事——只要字体能被渲染进程加载，导出即自动嵌入，无需手动改 PDF 字体表。

**两个层面的"内嵌"**：
1. **编辑器/预览内嵌**：`@font-face` 引用打包进应用的字体文件（woff2），预览在任意系统渲染一致。
2. **PDF 内嵌**：由 `printToPDF` 自动完成，嵌入文档用到的字形子集（矢量、文字可选），ATS 友好、体积小。

**使用手段（4 档）**：

| 手段 | 做法 | 体积 | 跨端一致性 | ATS | 适用 |
|---|---|---|---|---|---|
| **A 系统字体 + fallback** | `--resume-font:"PingFang SC","Microsoft YaHei","Noto Sans CJK SC",sans-serif` | 0 | 差（mac/win/linux 各异，他人打开 PDF 可能回退重排） | ✅ | v1.0 非默认模板 |
| **B 打包字体 + @font-face 自动嵌入（推荐默认）** | 选 OFL 许可 CJK 黑体，woff2 入 `src/renderer/assets/fonts/`，`@font-face` 定义后由 `--resume-font` 引用；printToPDF 自动子集嵌入 | +1 个 woff2（3–10MB，可压到 1–3MB） | 优（像素一致 + PDF 自包含） | ✅ | v1.0 默认模板 |
| **C 构建期子集化（体积优化）** | `fonttools`/`pyftsubset` 在 build 时把字体子集到简历常用字形（GB2312 等） | 1–3MB | 同 B | ✅ | B 的体积增强 |
| **D 用户自带字体（L3 远期）** | 用户选本地 TTF/OTF，`@font-face` 从 `file://` 加载并嵌入导出 | 0（用户自备） | 优 | ✅（须合法） | v2 |

**推荐定案（解析待拍板 #7 / 风险 #5）**：
- **v1.0 默认模板采用手段 B**：内嵌 1 款 **OFL 许可** CJK 黑体（如 Noto Sans CJK SC / 思源黑体），woff2 + `printToPDF` 自动子集 —— 跨端"所见即所投"自包含、ATS 安全；其余主题用手段 A（系统字体 + fallback）。
- 打包体积增量 = 单个 woff2（3–10MB；手段 C 可压到 1–3MB）。PDF 内嵌的是仅用到的子集，通常数百 KB。
- **许可是硬约束**：只可打包/嵌入 **OFL/SIL 等允许再分发 + 嵌入** 的字体。**系统字体（苹方/雅黑）禁止复制打包**，只能引用、不能内嵌——"内嵌思源黑体"必须自带一份 OFL 字体文件，而非复制系统字体。
- **ATS 安全口径（设计保证，非检查项）**：ATS 被筛的核心是"文字不可提取 / 图片化版式"。本项目默认模板采用手段 B（内嵌 OFL 矢量子集字体），文字天然可选中、非位图——**完全 ATS 安全**；系统字体（手段 A）同样文字可选。由此所有内置模板默认兼容 ATS，无需独立的"检查项"或兼容性标记（原 F17 已移除，ATS 改为设计保证）。

**与现有规划的一致性**：M0 验收已含"含中文字体的 HTML → printToPDF 成功"（经验教训 0.3），路径已验证可跑；手段 B 不引入新依赖、不破坏"模板=打印"铁律，可直接落地。

## 七、2026-08-05 修订：定位升级为开源免费（基于竞品调研）

> 依据《竞品与用户反馈调研.md》与用户决策（开源免费、个人第一款项目），对报告核心结论做如下修订：

### 7.1 定位变更

**原**：离线简历编辑器（许可 MIT 或闭源未定）
**新**：**开源免费 · 隐私优先 · 防盲信 AI 的简历工作台**（MIT），三大信任承诺：真正免费（无水印、无付费墙、不阉割）· 数据主权（全本地、代码可审计、BYOK）· 人工掌控（AI 辅助非替代）。

### 7.2 调研关键发现（支撑定位）

- **付费墙/订阅是竞品最大差评源**（Resume.io/Zety 差评第一模式：试用自动转订阅、取消困难、计费周期欺骗）——开源免费天然规避，是核心护城河。
- **隐私是深层痛点**（用户反感信息存第三方服务器）——离线 + 开源可审计 + BYOK 正中此需求。
- **AI 同质化被招聘官吐槽**——本项目禁止"一键生成简历"，AI 只做辅助编辑，差异化成立。
- **开源赛道已有同质玩家**（Magic Resume/OpResume/JadeAI，卖点重合）——本项目三板斧差异化：桌面形态 + 三步核对导入（独有）+ 中文原生。
- **ATS 兼容是刚需**——所有内置模板默认兼容 ATS（单栏/标准标题/系统字体/文字可选），从设计上规避被筛风险，无需独立检查界面。

### 7.3 计划调整摘要（与 §5/§6 对照）

| 项 | 原建议 | 修订后 |

## 八、提案评估：编辑器界面外观主题（深色 / 浅色 / 跟随系统）

> **评估日期**：2026-08-05
> **提案**：为**软件编辑界面**（应用主壳 + 编辑表单 + 对话框 + Tiptap 控件）增加「浅色 / 深色 / 跟随系统」三态外观主题。
> **重要界定**：这与 F4「简历模板主题」（CSS 变量 `--resume-*`，作用于简历输出）是**两件不同的事**，本期评估只谈前者。用户原话明确点出"不是简历，而是软件编辑界面"。

### 8.1 问题界定（先拆清楚，否则又是一笔糊涂账）

现有文档里所有"主题"都指 F4 简历模板主题：
- 顶栏「主题」下拉（线框 ⑬ 左栏 / ① 顶栏）、功能需求清单 F4、用户操作视角 §三"换模板/换主题"——全部是简历配色/字体/间距（CSS 变量 `--resume-*`）。
- F11 设置里写的"应用设置（语言、默认模板、主题、更新偏好）"中，"主题"= 简历默认模板/主题，是 F4 的持久化入口，**不是**界面外观。

也就是说，当前**没有任何一处定义"应用界面的暗/亮外观"**。而现有原型线框图是按"深色主题"画的（评估报告 §1.1 / 线框图 meta「深色主题」），那只是线框图的绘制约定，不代表应用具备主题系统。真实应用若只画死深色，浅色偏好用户（含大量白天办公场景，是多数）会直接流失——这与"开源免费 · 隐私优先 · 广纳用户"的定位相悖。

**结论**：需新增的是「界面外观主题」三态，与 F4 简历模板主题**正交、互不干扰**。建议在 F11 中把"主题"明确拆成两项：①「简历模板主题」（F4，`--resume-*`）；②「界面外观主题」（新增，浅色/深色/跟随系统）。

### 8.2 可行性判断：✅ 高（近乎零新增依赖，架构零冲突）

1. **技术栈天生为暗色而生**。shadcn/ui（Radix 基元）+ Tailwind v4 整套组件样式基于 CSS 变量令牌（`--background / --foreground / --card / --primary / --muted / --border / --input / --ring ...`），在 `:root` 定义浅色、在 `.dark` 定义深色，组件统一引用 `bg-background text-foreground` 之类。shadcn CLI 初始化（`M0` 已定案统一用）**默认生成 `:root` 与 `.dark` 两套变量块**——令牌地基白送，只需补一个"切换 + 持久化"的开关。
2. **Tailwind v4 暗色变体已就位**。v4 默认暗色基于 `prefers-color-scheme` 媒体查询；shadcn 的 v4 模板用 `@custom-variant dark (&:where(.dark, .dark *));` 改为「class 策略」（`.dark` 类挂到 `<html>`），正好支撑「显式浅色覆盖系统深色」的需求。
3. **Electron 原生支持"跟随系统"**。`nativeTheme.themeSource = 'system' | 'light' | 'dark'` + `nativeTheme.shouldUseDarkColors` + `nativeTheme.on('updated')` 事件，是桌面应用做系统主题同步的官方正解，无需任何第三方库。
4. **与"模板=打印"架构零冲突（最关键）**。简历预览（PreviewPane）必须**永远呈现真实纸张外观**（白底），否则 WYSIWYG 失效、导出 PDF 失真。只要两套变量命名空间彻底分开——应用 UI 用 shadcn 令牌（`--background` 等），简历模板用 `--resume-*`（F4）——并约定「`.dark` 类只作用于应用主壳与表单/对话框容器，**PreviewPane 强制重置为浅色纸张**」，二者就完全正交。F16 隐私打码（作用于打印态）不受影响；ATS 友好由模板设计保证（单栏 / 标准标题 / 矢量文字可选），与界面主题正交、亦不受影响。
5. **持久化/国际化/测试均有现成落点**。设置存 electron-store（F11）、文案走 react-i18next（F13）、测试用 Vitest/RTL/Playwright（F14 测试栈）——都不用新选型。

**唯一需写代码处**：① 一个 `useTheme`/ThemeProvider（切换 `.dark` 类 + 读系统）；② 设置项 UI（⑤ 设置屏加三态单选）；③ 启动防 FOUC（preload 注入初始类）；④ 系统变化监听（nativeTheme 'updated'）。全是小体量、低风险的标准实现。

### 8.3 实现方法（落地级）

**① 状态来源（单一事实源）**：在 F11 的应用设置 schema（electron-store）新增 `appearance: 'light' | 'dark' | 'system'`，默认 `'system'`。渲染进程用 Zustand 或 React context 暴露 `useTheme()`，读/写经 IPC 落到 electron-store（遵循"设置在主进程"的既有约定，与 F11/F12 一致）。

**② 应用机制（class 策略）**：`index.css`（shadcn 初始化产物）保持 `:root { 浅色令牌 }` 与 `.dark { 深色令牌 }`，加 `@custom-variant dark (&:where(.dark, .dark *));`。一个 `applyTheme(effective)`：`'dark'` 时 `document.documentElement.classList.add('dark')`，否则移除。组件统一用语义类，不写死颜色。

**③ "跟随系统"怎么算**：`appearance === 'system'` 时 effective = `nativeTheme.shouldUseDarkColors`（主进程判定，与操作系统一致，连原生标题栏同步）；渲染进程经 preload/IPC 拿状态，监听主进程转发的 `nativeTheme.on('updated')` 实时重算。显式 `'light'/'dark'` 直接覆盖系统。

**④ 防 FOUC（首屏闪烁）**：在 `@electron-toolkit/preload`（已在栈）里，于页面脚本执行前读取初始 `appearance` 并立即给 `document.documentElement` 加/去 `.dark`——preload 早于渲染进程 DOM 脚本运行，首帧前定底色，杜绝白屏闪一下变深。同时给 `BrowserWindow` 设与初始主题一致的 `backgroundColor`。

**⑤ 作用域护栏（必做，否则破坏"模板=打印"）**：`.dark` 仅作用于「应用主壳 + 编辑表单区 + 对话框 + Tiptap 编辑控件」。`PreviewPane`（简历模板组件容器）**显式重置为浅色纸张**：根节点固定浅色背景、只消费 `--resume-*`（F4），不继承 shadcn 暗色令牌。即深色界面里左边表单是暗的、右边简历预览仍是白纸——所见即所投。顶栏/侧栏图标用 `currentColor`（lucide 随令牌走）天然适配两态。

**⑥ 设置项 UI（落点）**：⑤ 设置屏新增「界面外观」分区：三态单选（浅色/深色/跟随系统），选项文案经 F13 i18n。可选增强：侧栏/顶栏放一键切换按钮（`appearance==='system'` 时切到显式态），属体验增益，非必须。

**⑦ 测试**：RTL 断言切换后 `document.documentElement` 的 `.dark` 类存在/缺失、`bg-background` 组件渲染正确；Playwright 切换刷新后从 electron-store 读回 `appearance` 一致，并模拟系统主题变化验证实时跟随。

### 8.4 工作量与里程碑建议

- **令牌地基：M0 顺手打底**（与 shadcn 初始化同一步，零额外成本；类比 F13 i18n 已前移 M0 避免后期返工——主题令牌同理，早建早省）。
- **设置项 UI + 持久化 + 系统跟随 + 防 FOUC：M1（F11 设置）或 M5 收尾阶段**落地，属"设置页加一个分区"的量级，低。
- **整体工作量：低**（核心代码 < 1 天，含测试）。

### 8.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| 防 FOUC 没做 → 启动闪白/闪深 | preload 首帧前注入 `.dark` 类 + 窗口 backgroundColor 同步 |
| `.dark` 漏到 PreviewPane → 简历预览变暗、WYSIWYG 失真 | 作用域护栏（8.3⑤）：PreviewPane 强制浅色纸张、只消费 `--resume-*` |
| 把"界面外观主题"和 F4"简历模板主题"混为一谈 → 设置项语义混乱 | F11 拆两项（8.1），变量命名空间分离（`--background` vs `--resume-*`） |
| 系统主题监听未清理 → 内存泄漏/多窗口串味 | 主进程 `updated` 监听在窗口关闭时反注册；多窗口共享同一 electron-store 值 |
| 浅/深两态对比度不达标（尤其 Tiptap 内语法/匹配高亮） | 标记色（`.grammar-error` / `.match-found`）选两态均可见的色值或按主题取不同明度 |
