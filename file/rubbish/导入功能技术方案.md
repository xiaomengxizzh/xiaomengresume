# xiaomengresume 导入功能技术方案（讨论稿）

> **日期**：2026-08-05（基于《技术栈.md》《功能需求清单.md》F6/F10 现状扩展）
> **范围**：Word / JSON / PDF / 图片四类导入的架构、路由判定、AI 介入边界
> **核心命题**：澄清"AI 识别"vs"技术抽取"的边界，重点探讨**非图片（文本型）PDF 的技术识别可行性**

---

## 〇、先泼盆冷水：你混淆了"读文字"和"懂结构"

用户诉求原文：「支持 word、json、pdf 和图片的导入，pdf 和图片支持 AI 识别，此外探讨一下非图片 pdf 技术识别的可行性」。

这里有个概念陷阱，必须先掰直：

- **图片 / 扫描件 PDF**：没有文本层，是像素。必须从像素里"认"出文字 → **必须用 AI 视觉（F10）或 OCR**。这部分"AI 识别"说得对。
- **非图片（文本型）PDF**：文件里已经内嵌了数字化文字（glyph + 坐标），根本不是"识别"问题，是"**抽取**"问题。`unpdf`（PDF.js）一行 `extractText(buffer)` 就能把字抽出来，**零 AI、离线、免费、瞬间完成**。

所以"非图片 PDF 技术识别的可行性"真正要问的是：**从文本型 PDF 抽出的文字流，能不能不靠 AI、纯用规则还原出简历结构（哪段是标题、哪行是 bullet、哪个是公司哪个是日期）？** 这才是值得探讨的技术问题。下文第四节专门拆。

---

## 一、四类导入统一管线（一张路由图）

```
文件入站
  │
  ├─ .json ───────► 直接反序列化 → Zod 校验 → 版本迁移 → 写入 store
  │                 （无需 AI，确定性）
  │
  ├─ .docx ───────► mammoth → HTML/纯文本 → AI generateObject 映射（F6 同款）
  │                 （文本型，无需 vision；结构靠 AI 映射 + 三步核对）
  │
  ├─ .pdf ────────► unpdf.extractText(buffer)
  │                 │
  │                 ├─ 文本充足/正常 ──► AI generateObject 映射（F6）★文本型主路径
  │                 │                   （可选：先用纯规则预解析，见第四节）
  │                 │
  │                 └─ 文本为空/乱码 ──► 判定为扫描件 → vision 多模态（F10）
  │
  └─ .png/.jpg ───► vision 多模态（F10）→ 文本 → F6 的 generateObject 映射
                    （图片只有这一条路）
```

**唯一的分流决策点**：PDF 抽文本后，文本量是否达标。
- 达标 → 走 F6（文本映射，**不碰 vision**）。
- 不达标/乱码 → 实为扫描件 → 走 F10（vision）。
- 这就是"这份 PDF 到底是图片型还是文本型"的判别器，写一次，全项目复用。

**所有非直接路径（docx / pdf文本 / pdf扫描 / 图片）最终都汇入同一个三步核对向导（F6/F10），不可跳过。** 这是防盲信 AI 的信任底线，不是优化项。

## 二、JSON 导入（最省心，零 AI）

- **场景 A（自家风味的 JSON）**：本应用导出的版本化简历（`F1` 的 `ResumeSchema` + `schemaVersion`）。导入 = `JSON.parse` → `ResumeSchema.safeParse` → 版本迁移函数 → 直接写入 store。纯确定性，无 AI、无映射、无歧义。
- **场景 B（外部标准 JSON，如 JSON Resume schema）**：反序列化后走一层字段映射（external → 内部 `ResumeSchema`），再三步核对。仍无需 AI——字段名是确定性的，写映射表即可。
- **结论**：JSON 导入是"读自家/标准格式"，不是"识别"，别往 AI 上靠。

## 三、Word 导入（当前技术栈的盲区，需补一个库）

### 现状缺口
《技术栈.md》3.9 只列了 `unpdf`（PDF），**完全没有 Word 解析库**。M4 要做 Word 导入，必须新增选型。

### 选型建议：`mammoth`
| 候选 | 结论 |
|---|---|
| **`mammoth`** ✅ | `.docx → 语义化 HTML`，能把 Word 的"标题/加粗/列表/表格"样式映射成 `<h1>/<strong>/<ul>`，**比裸文本多出结构信号**，对后续映射极友好。周下载量高、成熟、MIT。 |
| `docx` | 把 docx 当 DOM 解析，更底层但要从 XML 自己扒样式，工作量大。 |
| `officeparser` | 只抽纯文本，丢掉所有样式/结构信号，最裸。 |
| 直接解 zip 读 `word/document.xml` | 自找麻烦，等于手写 mammoth 一半功能。 |

**推荐 `mammoth`**：它给的 HTML 已经带 heading/list/strong 标签，等于免费送你一层粗结构。

### 管线
```
docx buffer
  → mammoth.convertToHtml({buffer})   // 得语义 HTML
  → （可选）优先用 HTML 的标签做本地启发式分段：<h1>/<h2> 当 section 标题，<ul><li> 当 bullet
  → 若启发式不足，抽取纯文本 → AI generateObject 映射（复用 F6 schema）
  → 三步核对向导
```

### 坑（必须写进风险表）
Word 简历的排版极脏：**用表格做布局、文本框、嵌入图片、美术字**。mammoth 对"标准样式"友好，对"表格当布局"会抽成一坨。所以 Word 导入**同样不能跳过三步核对**——AI 映射只是首轮，用户必须逐段确认。

### ESM 注意
`mammoth` 是 CJS，没有 ESM 构建。主进程已是 `"type": "module"`，需用**动态 `import('mammoth')`**（或 `createRequire`）引入，跟 AI SDK 的 ESM 约束不冲突。技术栈"ESM-only"章节需补一句说明。

## 四、★ 重点：非图片（文本型）PDF 的技术识别可行性

### 4.1 概念拆解：文本型 PDF 的"识别"其实是三件事

| 子问题 | 是什么 | 难度 | 现有方案 |
|---|---|---|---|
| **① 文本抽取** | 把内嵌 glyph 抽成字符串 | 几乎为零 | `unpdf` 已解决，离线免费 |
| **② 布局还原** | 从"文字+坐标"重建阅读顺序、栏目、段落、bullet | 中等 | 规则解析 / 布局库，**尚无现成好用的** |
| **③ 语义映射** | 判断"这段是工作经历标题 / 这家是公司 / 这行是日期" | 较难 | AI `generateObject`（F6）最稳 |

很多人把三者混为一谈喊"AI 识别 PDF"。真相：**① 根本不需要 AI；③ 用 AI 最省心；② 才是纯技术路线的主战场。**

### 4.2 "纯技术（无 AI）识别"可行性逐条评估

**① 文本抽取 —— 100% 可行，已落地。**
`unpdf` 底层 PDF.js，Node 原生、含 CMap 中文，抽中文无压力。这部分闭眼用，千万别为文本 PDF 上 vision（那是开倒车，见 4.4）。

**② 布局还原（无 AI）—— 部分可行，看排版脸色。**
纯规则/启发式能做的事：
- 用 **字体大小/字重** 判别标题（简历里大号粗体多半是 section 标题或姓名）。
- 用 **y 坐标聚类** 还原阅读顺序、分行分块；用 **x 坐标** 检测双栏。
- 用 **缩进 + 项目符号字符（•、–、-）** 识别 bullet。
- 用 **关键词字典**（工作经历/Experience、教育背景/Education、技能/Skills…）锚定 section 起点。

这套对**规整、传统的单栏简历**能恢复个七八成，且**确定性、零成本、隐私满分**——跟「本地确定性规则」的哲学一脉相承。
但对**创意双栏、表格布局、文本框、艺术字**会翻车：规则写不死所有奇葩排版，准确率掉得难看。

**③ 语义映射（无 AI）—— 不推荐硬刚。**
"这段到底是公司名还是职位"这种语义判断，硬写规则会维护到哭。让 LLM 用 `generateObject` 对着（带坐标的）文本直接吐 `ResumeSchema` 是最优解——LLM 凭内容推断语义，天然抗奇葩排版。这正是现有 F6 的设计，**文本 PDF 直接复用即可**。

### 4.3 推荐落地组合（分两档）

- **A 档（默认，AI 辅助）**：`unpdf` 抽文本（+ 可选坐标）→ `generateObject` 映射 → 三步核对。稳健、抗脏排版。就是现有 F6，文本 PDF 不用改。
- **B 档（隐私最大化 / 离线无 Key / 省钱）**：`unpdf` 抽文本 → **纯本地规则预解析**（自写启发式，无新依赖，或复用 unpdf 自带的 pdfjs 坐标）→ 产出"草稿结构" → 三步核对让用户补完 AI 没做的语义判断。
  - 这档正好呼应产品三大信任承诺里的"数据主权 + 人工掌控"：用户没填 Key 或勾了"纯本地"时，照样能导入规整文本 PDF，只是要自己多核对手动点。
  - **B 档不是替代 A 档**，是降级兜底。脏排版下 B 档质量有限，需明确提示用户"纯本地模式对复杂排版识别率有限，建议配置 Key 用 AI 映射"。

### 4.4 一个明确的"别这么做"
**不要对文本型 PDF 用 vision（渲染成图再让多模态认）。** 理由：
1. 文本型 PDF 已有完美数字文本，渲染成图反而**丢失精确文字、引入 OCR 误差**；
2. 多花 vision 调用成本 + 延迟 + 隐私暴露；
3. 质量不升反降。
vision 只服务于"真·没文本层"的扫描件/图片（F10）。判别器（第一节分流点）就是用来拦住这种浪费的。

### 4.5 可行性结论
| 问题 | 结论 |
|---|---|
| 非图片 PDF 能不能"技术识别"（抽文字）？ | **能，且已解决**（unpdf），不需要 AI。 |
| 能不能"纯技术"还原结构？ | **半能**：规整排版可规则解析，奇葩排版不行。 |
| 纯技术路线要不要做？ | **做一层轻量规则预解析当 B 档兜底**，但语义映射仍交给 AI（A 档）最稳。 |
| 文本 PDF 要不要用 AI 识别？ | 抽取**不用**；语义映射**用**（generateObject，非 vision）。 |
