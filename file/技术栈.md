## 二、分区技术栈（含选型理由与淘汰记录）

### 3.1 桌面壳与分发 [D6]
| 项 | 选型 | 理由 |
|---|---|---|
| 桌面壳 | **Electron**（~43.x，内置 Node 24） | 全球一致 Chromium 渲染（避免 Tauri 三端 WebView 碎片化），生态最成熟 |
| 打包 | **electron-builder** | 成熟、跨平台、支持便携版 zip |
| 自动更新 | **electron-updater** | electron-builder 生态标配 |

> **淘汰**：Tauri — 用户偏好 Electron；文档编辑需"模板=打印"像素一致，全球同一 Chromium 更省 QA。

### 3.2 语言、构建与工程 [D6]
| 项 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript**（strict mode） | 类型安全贯穿全栈 |
| 构建 | **Vite**（纯 SPA，无 SSR） | 极快；SPA 是桌面渲染进程的正确形态 |
| 主进程构建 | **electron-vite**（M0 验证） | 主/预加载/渲染三端一体打包 ESM TS 主进程 |
| 包管理 | **pnpm** | 严格依赖解析、快 |
| Lint/格式 | **ESLint** + **Prettier** + **typescript-eslint** | 标准组合 |

> **淘汰**：TanStack Start（SSR）— 桌面场景不需要服务端渲染。

### 3.3 渲染与 UI [D1]
| 项 | 选型 | 理由 |
|---|---|---|
| UI 框架 | **React 19** | 桌面生态最强，Tiptap / shadcn / AI SDK 均 React-first |
| 样式引擎 | **Tailwind CSS v4** | v4 已成熟；**M0 起统一 shadcn CLI + v4 生成全部样式，避免 v3/v4 混用** |
| 组件库 | **shadcn/ui**（Radix 基元） | 复制即拥有、可控性高、无障碍完善 |
| 图标 | **lucide-react** | 一致的图标语言 |

> **淘汰**：HeroUI → 偏重、定制受限。

### 3.4 状态管理 [D1]
| 项 | 选型 | 理由 |
|---|---|---|
| 全局状态 | **Zustand** | 轻量、无 boilerplate、TS 友好 |
| 撤销/重做 | **自维护轻量历史栈** | 核心功能不依赖半弃坑库；已验证可行 |
| 嵌套更新 | 暂不引入 **Immer** | Zustand 浅比较够用，等痛点再加 |

> **淘汰**：zundo（2 年未更新、16 open issue）、Redux（过重）。

### 3.5 编辑内核 [D1]
| 项 | 选型 | 理由 |
|---|---|---|
| 富文本 | **Tiptap v3**（ProseMirror，3.29.2） | 结构化富文本标杆 |
| 扩展 | **仅 MIT 免费扩展**（粗体/斜体/列表/对齐/下划线/链接/高亮/颜色） | 简历场景不需要 Pro 扩展，零许可成本 |

> **淘汰**：Lexical（生态年轻）、Plate/Slate（配置成本高）。

### 3.6 数据模型 [D1]
| 项 | 选型 | 理由 |
|---|---|---|
| Schema | **Zod**（`zod/v4` 子路径，AI SDK v7 peer 要求） | 同时服务 UI 校验、AI 结构化输出、IPC 入口、持久化——单一事实源 |
| 存储格式 | **版本化 JSON** | 可读、可备份、可 diff |

#### 3.6.1 岗位数据模型（WP-R1 · R 阶段定案，F19） [D5]

> 对应《项目实现情况.md》§2.1 WP-R1；待拍板 #12 按默认建议落定。

- 新增独立实体 `Job`（岗位），与简历平行、互不直接耦合：`src/shared/schema/job.ts` 导出 `JobSchema` / `Job` / `createEmptyJob`：

```ts
// src/shared/schema/job.ts（Zod v4）
const DateStr = z.string().regex(/^\d{4}(-\d{2})?$/, '日期格式应为 YYYY 或 YYYY-MM').or(z.literal('')).optional();
export const JobSchema = z.object({
  id: z.uuid(),
  name: z.string().min(1),
  appliedAt: DateStr,              // 复用 F1 DateStr（YYYY 或 YYYY-MM）
  requirements: z.string(),        // 岗位要求纯文本（#12 默认建议，复用 F9 JD 文本化）
  createdAt: z.string(),           // ISO 8601，主进程写入
  updatedAt: z.string(),
});
export type Job = z.infer<typeof JobSchema>;
```

- `ResumeSchema` 增**可选** `boundJobIds: z.array(z.string().uuid()).default([])`（T 批 WP-T2 由单值 `boundJobId` 升为数组）——**仅增不改**、`schemaVersion` 保持 `z.literal(1)` 不升（与 F9 `targetJobDescription` 同策略）；`migrate()` 现有 `case 1` 直通无需改动，旧 JSON 缺该字段 → Zod `default([])` 自然兼容，**零迁移**。`migrate()` 骨架预留 `boundJobId→boundJobIds` case 注释（见《项目功能.md》F19 数据层落地点），本批无历史数据永不触发。
- 岗位存储 `userData/jobs/<id>.json`（`src/main/files/job-store.ts` 仿 resume-store，复用 `.tmp`/`.bak` 机制，见 §3.11.2）；删除岗位不级联删除简历（软引用，UI 判空）。
- 岗位数据模型详情（生命周期 / IPC / 备份范围）见《项目功能.md》F19 数据层落地点。

#### 3.6.2 summary 英文版字段（WP-T6 · T 阶段定案，对应 #25）

- `SummarySchema` 增**可选** `enContent: RichTextSchema.optional()`——**仅增不改**、`schemaVersion` 保持 `z.literal(1)` 不升（与 F9 `targetJobDescription`、F19 `boundJobId` 同策略），`migrate()` 现有 `case 1` 直通无需改动，旧 JSON 缺该字段 → Zod optional 自然兼容，**零迁移**。

```ts
// src/shared/schema/resume.ts —— 仅追加 enContent，不改 content
export const SummarySchema = z.object({
  content: RichTextSchema,                                  // 既有，不变
  enContent: RichTextSchema.optional().describe('英文版自我评价（F20 翻译模式产出，仅增不改）'),
});
export type Summary = z.infer<typeof SummarySchema>;
```

- 顶层 `ResumeSchema` 的 `summary` 仍指向 `SummarySchema`，`schemaVersion: z.literal(1)` 首字段**不变**；`createEmptyResume()` 的 `summary` 保持 `{ content: EMPTY_DOC }`（`enContent` 省略 = undefined）；`migrate()` 不动（`case 1` 直通）。

### 3.7 模板与主题 [D2]
| 项 | 选型 | 理由 |
|---|---|---|
| 模板 | **React 组件** + **CSS 变量**主题（`--resume-*`） | 靠变量切主题，零组件重复 |
| 分页 | **CSS `@page` + `page-break-*`**（Chromium 原生） | 够用，不引入第三方分页库 |
| 高保真预览 | 无额外依赖 | 预览 = 同一套 React 模板组件 + CSS 主题（矢量、文字可选） |

> **淘汰**：Paged.js（约 3 年未更新，项目停滞）。

#### 3.7.1 格式一致性（预览 = 投递）
右侧模板预览与导出（`@react-pdf/renderer` 消费同一 React 模板组件数据）是**同一套数据模型 + 主题令牌**（"模板=打印"）。所见即所投；左侧表单只是数据入口，不是最终外观。导出为**矢量、文字可选**，天然 ATS 友好。

#### 3.7.2 模板"可编辑性"分级
| 层级 | 能力 | 结论 |
|---|---|---|
| L1 换皮 | 预设模板切换 + 调 CSS 变量 | ✅ 必做（v1.x 默认） |
| L2 重组 | 模块显隐 + 拖拽排序（`sectionOrder`/`hidden`） | ✅ 增强候选（v1.x） |
| L3 自定义 | 用户上传模板（声明式 DSL + 沙箱） | ⚠️ v2（模板市场）；clean-room 禁执行不可信代码 |
| L4 可视化拖拽 | Canva 式自由排版 | ✗ 非目标（工作量巨大、与"模板=打印"冲突） |

> 竞品"海量模板"本质是**少数布局引擎 × 大量参数化皮肤**的乘法（调研结论），印证 L1/L2 工业化可行。

#### 3.7.3 L3 本质难点与 AI 边界
L3 难点在**安全边界**（用户模板 = 不可信代码，须走受限 DSL + 沙箱校验）+ **渲染一致性**（须守"模板=打印"）+ **数据映射回写**，不在"看懂版式"。AI 不解决 L3 本质矛盾，只做两件务实的事：**(A) AI 选模板**（参考图 → 推荐最相近预设模板 + 微调主题，本质是 L1/L2 增强）；**(B) AI 辅助写受限 DSL**（仍过沙箱校验）。真·任意 HTML 模板安全渲染仍是 v2 硬骨头。

#### 3.7.4 字体嵌入策略（已定案 · T 阶段 #23 修订）
| 项 | 做法 |
|---|---|
| 手段 B（v1.0 默认模板） | 内嵌 **OFL 许可** CJK 黑体（Noto Sans CJK SC / 思源黑体），woff2 入 `src/renderer/assets/fonts/`，`@font-face` + `--resume-font` 引用；导出 PDF 由 **@react-pdf/renderer 嵌入（自动子集）**，跨端一致 + ATS 安全 |
| 手段 A（系统字体，v1.0 静态白名单） | 系统字体静态白名单（`src/shared/constants/fonts.ts`，跨平台常见中英文字体名），零依赖；默认「系统默认」= fallback 链 `"PingFang SC","Microsoft YaHei","Noto Sans CJK SC",sans-serif`；**v1.0 不引入 font-list 枚举**（运行期探测已装字体），列为 v2 候选 |
| 手段 C（体积优化） | 构建期 `fonttools`/`pyftsubset` 子集到 GB2312，压 1–3MB |
| 手段 D（v1.0 导入字体，`font://` 协议） | 设置屏「导入字体」→ `dialog.showOpenDialog`（filters: ttf/otf/woff/woff2，上限 20MB）→ 主进程复制 `userData/fonts/<id>.<ext>` → 注册自定义协议 `protocol.handle('font', ...)` 服务本地字体 → 渲染进程动态注入 `@font-face`；清单 `SettingsSchema.importedFonts`；**导入时弹许可提示：字体许可用户自担、仅本机使用不重新分发**；导出 PDF 经 @react-pdf/renderer 嵌入（与手段 B 同机制） |
| **许可硬约束** | 只可打包/嵌入 **OFL/SIL 等允许再分发+嵌入** 的字体；**系统字体（苹方/雅黑）禁止复制打包**；导入字体仅本机使用、不随应用重新分发（用户自担许可） |

> 关联：导入字体数据层契约见《项目功能.md》F18 扩展；`SettingsSchema.importedFonts` 定义见 §3.11（WP-T4）。

#### 3.7.5 模板/主题技术落地点（WP-P2 · P 阶段定案）

- **模板注册表 `registry.ts`**（`src/renderer/templates/registry.ts`）：`id → { component, thumbnail, nameKey }` 映射，切换仅改 store 的 `templateId`，`PreviewPane` 按 id 取组件渲染；3 套模板共享同一套渲染函数，仅主题 / CSS 变量区分，避免组件重复。
- **主题 CSS 变量方案**：`--resume-font` / `--resume-accent` / `--resume-spacing` 三变量驱动换肤，`ThemeProvider` 写 `.resume-root` 的 style 变量；`--resume-font` 承接 F16 / 中文字体策略（默认指向内嵌 OFL 黑体）。
- **分页 `@page` 口径（铁律）**：`@media print { @page { size: A4; margin: 15mm } .resume-section, .resume-entry { page-break-inside: avoid } }`；条目跨页不硬截（`page-break-inside: avoid`），章节分页交 Chromium 自然流动。
- **ATS 默认兼容设计保证**：三套模板一律单栏 + 标准 section 标题（真实 `h2` 文本）+ 内嵌 OFL 矢量字体 + 文字可选中；不设置独立 ATS 检查界面 / 角标 / 导出卡片（见《项目功能.md》ATS 段）。
- **L2 模块排序（明确不进 v1.0）**：`sectionOrder` / `hidden` 拖拽显隐与排序列为增强候选（v1.x），v1.0 不做；数据模型无需为 L2 预留字段（保持干净）。
- **v1.0 内置 3 套模板**：`classic`（经典单栏）/ `modern`（现代单栏，accent 色条）/ `compact`（紧凑单栏），均为单栏 ATS 友好，差异化仅版式密度与视觉节奏。

### 3.8 导出（4 格式）— M2 / M3 [D2]

| 项 | 选型 | 理由 |
|---|---|---|
| 引擎 · 文字版 PDF | **`@react-pdf/renderer` 纯代码生成**（React 组件描述布局 → 直接产出 PDF 二进制流） | 矢量、文字可选、自动换行/分页/文本测量；**零 GPU/零隐藏窗口/零 loadURL**（printToPDF 实测在无 GPU 机器永不 resolve，2026-08-08 重构，见《PDF导出_完整解决方案.md》归档件）；v4.1+ 官方支持 React 19 |
| 引擎 · 图片版 PDF | `webContents.capturePage()` 逐页截图 → **`pdf-lib` 合成**（候选，见 §3.18） | 纯 JS 合成 PDF 图像对象，无原生编译、无额外二进制，过 G.2 三问 |
| 引擎 · 图片格式 | `webContents.capturePage()` 逐页存 PNG（默认）/ JPG（可切 + 品质参数） | 复用同一截图管线；多页每页一文件 `简历名-页N.<ext>` |
| 引擎 · JSON 版本 | `ResumeSchema` 序列化（含 `schemaVersion`）落盘 `.json` | 确定性、零 AI、便于再导入（见 §3.19 / #4） |
| 选项 · 仅第一页（D13） | **`pdf-lib` 裁第一页**（保留原 Info dict：Title/Creator 等） | 旧 CSS `overflow` 截断方案随 printToPDF 退役（2026-08-08） |
| 时序 | 主进程直接生成，无渲染窗口等待；打印/截图类路径保留等 `document.fonts.ready` | 文字版 PDF 无需浏览器渲染，任何环境可跑 |
| 目录优先级 | 显式 `folderPath` > `SettingsSchema.export.lastFolder` > `storage.folderPath`(F21) > 系统下载目录 | 默认「简历存储位置」，记忆上次选择（#22） |
| 进度 | `webContents.send('export:progress', { phase, ratio })` | 渲染进程进度条，主进程无 UI |

> **淘汰**：html2canvas + html2pdf.js（栅格化）、printToPDF 隐藏窗口方案（GPU 依赖，2026-08-08 退役，print/pdf.ts 仅保留供冒烟与 imagePdf v1.1 使用）；零依赖手写 PDF 图像对象工作量大不推荐。

**IPC 契约（`export:run`，取代原 `pdf:export`）**：
- 通道 `'export:run'`，参数 `ExportRunArgs { format, folderPath?, pages?, privacyMode }`（`pages: 'all'|'first'`、`privacyMode` 为 2026-08-08 纯代码链路新增），返回 `ExportRunResult { canceled, filePath?, error? }`（类型冻结于 `src/shared/ipc-channels.ts`）。
- 进度事件 `export:progress`（`{ phase: 'render'|'write'; ratio }`），preload 暴露 `window.electronAPI.export.run`。
- `SettingsSchema` 新增 `export: { lastFolder?: string }`——落盘成功后回写，记忆用户上次导出目录（#22 默认建议 ③）。

### 3.9 AI 能力层 [D4]
| 项 | 选型 | 理由 |
|---|---|---|
| SDK | **Vercel AI SDK v7**（`ai` 7.0.52） | clean-room 下替代手写多供应商层；统一流式/结构化/多模态 |

#### 3.11.3 简历存储位置主存迁移（WP-S3 · S 阶段定案，对应 #18 方案 B） [D5]

> 2026-08-06 用户澄清：与「同步/云盘」无关，纯本地存储文件夹；原名「同步文件夹」废弃，F21 = 简历存储位置管理。

- **SettingsSchema 增 `storage: { folderPath?: string; lastUsedAt?: string }`**（默认缺省 = `defaultStorageFolder`；无 autoSync/lastSyncAt 等同步语义残留）。
- **主存基准变更**：`resume-store.ts` 基目录由 `userData/resumes/` 改为读 `storage.folderPath`（缺省回落默认），F11 三件套（`.tmp` 锁 / `.bak` 轮转 / `backup:export`）同步以 `<storageFolderPath>/` 为基准；**jobs 仍 `userData/jobs/<id>.json`**（R 批定案，不卷入）。
- **默认策略（用户拍板 = 默认文档目录 + 可改）**：`defaultStorageFolder = path.join(app.getPath('documents'), 'xiaomengresume')`，首装 `fs.mkdirSync({ recursive: true })` 自动建（可见易找，非隐藏 `%APPDATA%`）；⚠️ caveat：若系统将「文档」重定向到 OneDrive/iCloud（Windows 常见），默认位置实落同步盘——属系统行为，用户可在设置屏「更改位置」到非同步目录（应用零云盘 SDK）。
- **更改位置自动迁移**（`src/main/files/storage-migrate.ts`）：校验新位置可写 → 拷贝旧位置全部 `.json` + `.bak.*` → 成功后切 `storage.folderPath` 并提示迁移数 → 失败不切换、旧数据不动；**不删旧文件**。
- **IPC 增补**（冻结于 `src/shared/`）：`storage:choose` / `storage:get`（`{ defaultPath, currentPath, exists }`）/ `storage:set`（应用+迁移）/ `storage:reset`（重置默认，二次确认）/ `storage:open`（`shell.openPath`）；preload 暴露 `window.electronAPI.storage.{choose,get,set,reset,open}`。
- **`backup:export` 范围**：`<storageFolderPath>/`（简历 .json+.bak）+ `userData/jobs/`（.json+.bak）；排除项不变（不含 logs、不含 API Key 明文）。
- **风险**：纯本地文件夹无同步服务干扰；仅用户自选同步盘内目录时存在同步服务扫 `.tmp/.bak`、多设备并发覆盖风险（用户自担，文档提示可把 `.tmp/.bak` 加入同步排除列表）。

#### 3.11.4 最近简历列表数据层（WP-T1 · T 阶段定案） [D5]

> 对应待拍板 #20 按默认建议落定；插入位置 = §3.11 系列内，紧接 §3.11.3 之后。

**meta 字段定义（主进程写入，仅增不改）**：
- 每份简历 JSON 顶层可选 `meta: { createdAt?, updatedAt?, lastOpenedAt? }`，全部 ISO 8601 字符串，**由主进程 `resume-store.ts` 写入**，渲染进程不直写。
- `createdAt`：首次 `resume:save` 时若缺失则补写；`updatedAt`：`resume:save` 每次刷新；`lastOpenedAt`：`resume:open` 每次刷新。
- 旧简历无 `meta`：主进程在 `resumes:recent` 计算 `lastActivityAt` 时回退取 `updatedAt` / `createdAt` / 文件 `mtime` 三者最大，**不回写磁盘**（零迁移、零噪声）。

**`resumes:recent` IPC 契约（冻结于 `src/shared/`，与 `resume:*` 同域）**：

| 项 | 说明 |
|---|---|
| 通道 | `resumes:recent`（invoke，无参数） |
| 返回 | `{ id: string; name: string; lastActivityAt: string; lastEditedAt?: string; lastOpenedAt?: string }[]` |
| 排序 | 按 `lastActivityAt` 倒序（`lastActivityAt = max(updatedAt, lastOpenedAt, createdAt)`） |
| 主进程职责 | 扫描 `<storageFolderPath>/`（§3.11.3，缺省回落 `userData/resumes/`）→ 逐份读 `<id>.json` → 取 `basics.name`（空则别名/文件名兜底）→ 计算 `lastActivityAt` → 倒序返回；跳过 `.bak`/`.tmp`；路径穿越防护（id 校验 uuid） |
| preload | `window.electronAPI.resumes.recent` |

**`resume:open` / `resume:save` 字段刷新语义**：
- `resume:save`：写 `meta.updatedAt = now`；`meta.createdAt` 缺失则补；走 §3.11.1 完整数据安全链路（`.tmp` 锁 + `.bak` 轮转）。
- `resume:open`：写 `meta.lastOpenedAt = now`（`createdAt` 缺失补写）；轻量原子写，**不触 `.bak` 轮转**（避免每次打开产生冗余备份）；仍走 `.tmp` 锁保证原子性。
- 两者均**不升 `schemaVersion`**（保持 `z.literal(1)`），`migrate()` 无需改动。

**SettingsSchema 字段**：本包**无需**新增 `SettingsSchema` 字段（`lastEditedResumeId` 已承担记忆上次打开）；若后续需「最近列表条数上限」可经 `SettingsSchema.maxBackups` 风格扩展。

#### 3.11.5 字体设置字段（WP-T4 · T 阶段定案，对应 #23） [D5]

> 字体数据层 + 令牌落点。**仅字体字段**，不涉 `language`（归 WP-T5）；与 F11 既有 `theme` 字段关系：移除 `resumeSpacing`，增 `uiFont` / `resumeFont` / `importedFonts`。

- **字段定义（`src/shared/schema/settings.ts` 增字体段）**：

```ts
import { z } from 'zod/v4';

export const ImportedFontSchema = z.object({
  id: z.uuid(),                                  // 字体唯一 id（uuid v4）
  fileName: z.string(),                          // 原始文件名（展示用）
  family: z.string(),                            // @font-face family 名（用户选择时写入 resumeFont/uiFont）
  addedAt: z.string(),                           // ISO 8601，主进程写入
});
export type ImportedFont = z.infer<typeof ImportedFontSchema>;

export const FontSettingsSchema = z.object({
  uiFont: z.string().default('system default'),        // UI 字体：应用壳/功能屏全局 font-family
  resumeFont: z.string().default('system default'),    // 简历字体：覆盖 --resume-font
  importedFonts: z.array(ImportedFontSchema).default([]), // 导入字体清单
});
```

- **落码要点**：
  - `uiFont` / `resumeFont` 取值 = `'system default'` 或具体 family 名（来自系统字体白名单 `fonts.ts` 或 `importedFonts[].family`）。
  - `importedFonts` 由主进程 `font:import` handler 写入（复制文件 + 注册 `font://` 协议 + 弹许可提示）；移除经 `font:remove` 删文件并注销。
  - **与 WP-T5 `language` 字段互不重叠**：本包只定义字体（`uiFont` / `resumeFont` / `importedFonts`），`language` 由 T5 在外观屏整合布局中负责。
  - 既有 F11 `theme: { resumeFont; resumeAccent; resumeSpacing }` 修订为：`theme.resumeAccent` 保留（全局默认主题色，被 `ResumeSchema.layout.themeColor` per-resume 覆盖，见 F4 修订）；`resumeSpacing` **移出全局设置**——**2026-08-07 修订：不删除，改由 `ResumeSchema.layout` 承载（per-resume 可调，模板预设值作默认）**；`resumeFont` 上提到 `FontSettingsSchema.resumeFont`（单一事实源，缺省回落模板/系统默认）。

### 3.16 统一管线与分流决策
```
文件入站
  ├─ .json ───► 反序列化 → Zod 校验 → 版本迁移 → 写入 store（无需 AI，确定性）
  ├─ .docx ───► mammoth → 语义 HTML/纯文本 → AI generateObject 映射（F6 同款）
  ├─ .pdf ────► unpdf.extractText(buffer)
  │             ├─ 文本充足 ──► AI generateObject 映射（F6）★文本型主路径
  │             │                （可选：先纯本地规则预解析，B 档）
  │             └─ 文本为空/乱码 ──► 判扫描件 → vision 多模态（F10）
  └─ .png/.jpg ► vision 多模态（F10）→ 文本 → F6 的 generateObject 映射
```
- **唯一分流决策点**：PDF 抽文本后字符数是否达标（阈值暂定 100，M4 实测调参，待拍板 #3）——达标走 F6（**不碰 vision**），不达标判扫描件走 F10。
- 所有非直接路径（docx / pdf 文本 / pdf 扫描 / 图片）最终汇入**同一个三步核对向导（F6/F10），不可跳过**——防盲信 AI 信任底线。

### 3.17 各类型细节
- **JSON**：场景 A 自家版本化 JSON（`ResumeSchema` + `schemaVersion`）= 纯确定性导入；场景 B 外部标准（JSON Resume）走字段映射层（待拍板 #4：v1.2 先认自家 + 留扩展点）。**不需要 AI**。
- **Word**：新增依赖 **`mammoth`**（.docx → 语义 HTML，自带 heading/list 结构信号）；CJS，主进程**动态 `import('mammoth')`**；Word 排版脏（表格布局/文本框/艺术字），**同样不可跳过三步核对**。已拍板：Word 进 v1.2（M4）。
- **PDF（文本型）**：三个子问题——① 文本抽取（unpdf，零 AI，已解决）；② 布局还原（规则解析，规整排版可行）；③ 语义映射（AI `generateObject` 最稳）。落地两档：
  - **A 档（默认，AI 辅助）**：unpdf 抽文本 → `generateObject` 映射 → 三步核对。
  - **B 档（纯本地，隐私最大化）**：unpdf 抽文本 → 自写启发式规则预解析（section 关键词锚定 + 基础 bullet，复用 pdfjs 坐标，零新依赖）→ 草稿结构 → 三步核对补语义（粒度待拍板 #2）。**B 是降级兜底不是替代 A**。
  - **明确禁止**：对文本型 PDF 用 vision（渲染成图再认）——丢精度、贵、慢、隐私差。vision 只服务真·无文本层的扫描件/图片。
- **图片/扫描 PDF**：只有 vision 一条路；复用 F6 三步向导 + 视觉模型双向守卫（纪律见《项目规范.md》4.4）。

#### 3.19 导入细化定案（WP-P4 · P 阶段）

> 本节落定《项目实现情况.md》§2.2 待拍板 #2（B 档粒度）、#3（PDF 文本空阈值）、#4（JSON 是否兼容外部 schema），并补充 mammoth 接入点（Word 已拍板进 v1.2，见 #1）。内容按 A/B/C/D 四段组织，可直接并入《技术栈.md》三。

##### A. B 档规则粒度（对应 #2）

**定位**：B 档是文本型 PDF 导入的**纯本地降级兜底**（`unpdf.extractText` 后、走 A 档 `generateObject` 之前的省钱/隐私最大化预解析），**不是 A 档的替代**——当排版脏乱导致本地规则失效时，必须提示用户切 A 档（AI `generateObject` 映射）。A 档仍是默认主路径。

**输入**：`unpdf.extractText(buffer)` 产出的纯文本（含换行与少量空行，无坐标层；坐标复用走 A 档路径，B 档只用文本流）。

**规则集（做到「section 分段 + 基础 bullet」即可）**：

1. **文本清洗（前置）**
   - 折叠多余空行（连续 `>1` 空行压成 1 行）；剔除**纯页码行**（独立一行的 `^\d+$`）、页眉页脚装饰线（`---`、`===` 等）。
   - 不剔除内容字符，只去噪声行，避免误删 bullet。

2. **section 分段（关键词锚定）**
   - 维护一份**中英双语 section 关键词锚点表**，按行首/行内独立词匹配（大小写不敏感，英文去标点）：
     | 本地 section | 中文锚点关键词 | 英文锚点关键词 |
     |---|---|---|
     | `basics` | 基本信息、个人资料、联系信息 | Profile、Contact、Personal |
     | `summary` | 自我评价、个人简介、个人概述 | Summary、Objective、About |
     | `education` | 教育经历、教育背景、学历 | Education、Academic |
     | `work` | 工作经历、实习经历、工作经验 | Experience、Employment、Work |
     | `projects` | 项目经验、项目经历 | Projects、Project Experience |
     | `skills` | 技能、专业技能、技能特长 | Skills、Technical Skills |
     | `certificates` | 证书、资格认证 | Certifications、Certificates |
     | `languages` | 语言能力、外语 | Languages |
   - 命中锚点行 → 作为该 section 的**起始边界**；下一锚点行之前的所有文本归入上一 section。无锚点行时归入「未分类」暂存段。
   - 锚点行本身不入内容，仅作分隔；匹配阈值：行中**独立成词且非其他词子串**（避免「项目」误命中「项目经理」之类，用单词边界 `\b`/中文前后非汉字判定）。

3. **基础 bullet 识别（section 内行级）**
   - 行首符号命中以下任一记为 bullet 项：`-`、`•`、`·`、`*`、数字序号（`1.`/`1)`/`①`/`（1）`）`、缩进 `+`/-`。
   - bullet 行提取为 `items: string[]`，归到当前 section（优先 `work`/`projects`/`skills`；`skills` 段额外做逗号/顿号/分号切分，拆成多技能项）。
   - 非 bullet 行作为该 section 的**自由文本/段落**（如 `basics` 的姓名行、联系方式行原样保留）。

4. **脏排版判定与提示切 A 档**
   - 触发以下任一即判定「本地规则不可靠」，**B 档产出仅作预览草稿，UI 必须提示"检测到多栏/表格/文本框等复杂排版，建议改用 AI 精准映射（A 档）"并给出一键切 A 档入口**：
     - 命中表格残余信号：行内含 `|` 分隔或连续制表符 `\t` 列对齐、或 `unpdf` 文本出现大量重叠/错位字符（如同一坐标多文本碎片）；
     - 多栏特征：短行（`< 20` 字）密集交替且无明显 bullet，疑似并排双栏；
     - 文本框/艺术字：出现孤立短语悬浮（无 section 归属、无 bullet、非联系方式）；
     - 锚点命中率 < 1（整篇无任何已知 section 关键词）——说明非标准简历或纯设计稿。
   - 即便无脏排版提示，B 档结果仍**必须过三步核对向导**补语义（字段归位、bullet 拆细），B 档只负责"先分段"，不负责"映射正确"。

**零新依赖**：B 档规则预解析**完全复用 `unpdf` 已抽文本 + 自写启发式函数**（`src/main/files/pdf-parse-rules.ts`），不引入任何新包；复用《技术栈.md》§3.18「B 档规则预解析（无）」结论。

**落码形态**：
```
extractText → cleanText → splitBySectionAnchors(text) → perSectionExtractBullets()
  → { sections: { id, type, rawText, items? }[], dirtyLayout: boolean }
  → 若 dirtyLayout: 提示切 A 档
  → 否则: 草稿结构喂入三步核对向导（用户补语义）
```

##### B. PDF 文本空阈值（对应 #3）

**唯一分流决策点**：PDF 抽文本后是否走 vision，**仅在 `.pdf` 路径生效**（`.json`/`.docx`/图片不触发此阈值；图片/扫描 PDF 由文件类型直接判 vision，不经阈值）。

**默认值**：`PDF_TEXT_EMPTY_THRESHOLD = 100`（字符数）。

**判定逻辑**：
1. `text = unpdf.extractText(buffer)`，先做清洗：剔除纯空白（`\s`）、剔除**乱码噪声**（连续不可打印/替换字符 `�` 占比 > 30% 的行视为乱码，不计入有效字符）。
2. 计算**有效字符数** `len = text.replace(/\s+/g,'').replace(/�/g,'').length`。
3. `len < 100` → 判定为扫描件/无文本层 → 走 F10 vision 多模态（同图片路径）。
4. `len >= 100` → 文本充足 → 走 F6 文本型主路径（A 档 `generateObject` 或 B 档本地规则）。

**阈值调参说明（M4 实测）**：
- `100` 为 P 阶段暂定默认值，属保守下限（多数真实简历文本页有效字符 >> 100）。
- **M4 实测调参**：用 20–30 份真实样本（含纯图片扫描件、文字型 PDF、图文混排）跑 `unpdf` 抽文本，统计扫描件与文本型的字符数分布交叉点，确定最终阈值（预期落在 50–200 区间）；调参后更新本常量并记入《项目日志.md》（集成者职责）。
- 阈值以**常量 + 注释**形式落 `src/main/files/import-config.ts`，便于 M4 单点修改，不硬编码在多处。

**护栏**：阈值只解决"有没有文本层"，不解决"文本准不准"；即便 `len >= 100`，脏排版仍按 A 段规则提示切 A 档。文本型 PDF **绝不**经 `render→图片→vision` 路径（《项目规范.md》§4.4 铁律）。

##### C. JSON schema 策略（对应 #4）

**两类 JSON 导入场景**：

- **场景 A · 自家版本化 JSON（主路径，v1.2 首发即支持）**
  - 格式：`ResumeSchema`（`src/shared/schema/resume.ts`）导出 + 顶层 `schemaVersion` 字段。
  - 流程：**纯确定性导入，无需 AI**——反序列化 JSON → Zod 校验（`ResumeSchema.safeParse`）→ 版本迁移（`migrate(data)` switch-case，见《技术栈.md》§3.6 /《项目规范.md》4.2）→ 写入 store。
  - 校验失败（字段缺/类型错）→ 报具体字段错误，引导用户修正或走其他导入方式；不静默丢字段。

- **场景 B · 外部标准（JSON Resume）**
  - 当前决策（#4 默认建议）：**v1.2 先认自家格式**，`schemaVersion` 存在且匹配即走场景 A；非自家格式（如 `resume.json` 含 `basics/works/volunteer` 的 JSON Resume v1.2 结构）**暂不实现字段映射**，导入时提示"暂仅支持 xiaomengresume 导出格式，外部 schema 将在后续版本支持"。
  - **映射扩展点（预留，不实现）**：在 `src/main/files/json-import.ts` 预留 `FieldMapper` 接口（输入外部对象 → 输出 `ResumeSchema` 形状），接口签名固定、实现留 `// TODO WP 后续`；后续接 JSON Resume 时只补一个 `jsonResumeMapper` 实现，不动管线。
    ```ts
    // 预留扩展点（v1.2 不实现，仅定接口）
    export interface FieldMapper<T> {
      detect(input: unknown): boolean;          // 识别是否为该外部 schema
      map(input: T): z.infer<typeof ResumeSchema>; // 映射到自家模型
    }
    ```
  - 明确：**JSON 导入全程不需要 AI**（确定性反序列化 + 映射），与《技术栈.md》§3.17 结论一致。

##### D. mammoth 接入点（Word .docx 导入）

**新增依赖**：`mammoth`（.docx → 语义 HTML），是导入四路中**唯一实质新增依赖**（《技术栈.md》§3.18）。

**模块形态**：CommonJS（CJS）包。主进程**动态 `import('mammoth')`**（AI SDK v7 已强制主进程 ESM 入口，见《技术栈.md》§3.9；CJS 包经动态 `import()` 在 ESM 主进程内按需加载，避免顶层 import 破坏 ESM 约束），不写入 `dependencies` 静态顶层 import。

**接入流程**：
1. `buffer = readFile(filePath)` → `const mammoth = await import('mammoth')`。
2. `const { value: html } = await mammoth.convertToHtml({ buffer })` → 得到**带语义结构的 HTML**（mammoth 保留 heading `<h1>-<h6>`、列表 `<ul>/<ol>/<li>`、段落 `<p>` 等结构信号）。
3. **优先用标签启发式分段**（无需 AI）：
   - `<h1>-<h3>` 视为 section 标题锚点（同 A 段关键词表做中英文映射）；
   - `<ul>/<ol>` 内 `<li>` 视为 bullet 项；
   - `<p>` 视为自由文本。
   - 标签信号充足（命中 ≥ 1 个 section 锚点）→ 直接产出草稿结构，喂三步核对向导。
4. **标签信号不足**（如 Word 用样式而非语义 heading、或大量文本框）→ 抽取纯文本（`mammoth.extractRawText`）→ 走 F6 `generateObject` 同款 AI 映射（A 档）。
5. **三步核对不可跳过**：无论标签启发式还是 AI 映射，Word 导入结果**同样汇入同一三步核对向导**（① AI/规则首轮 → ② 并排预览原文 vs 结构化 → ③ 逐段核对/修改 → ④ 确认写入），UI 不提供"一键导入"。
6. **脏排版提示**：Word 表格布局/文本框/艺术字导致结构信号丢失时，提示用户切 AI 映射（同 B 档脏排版逻辑），并复用 F6 三步向导。

**四路汇入同一向导**：`json` / `docx` / `pdf文本` / `pdf扫描+图片` 四条导入路径，最终产物均为「结构化草稿 + 原文快照」，统一进入**同一不可跳过三步核对向导**（数据完整性底线，《项目规范.md》§4.5）。四路差异只在"首轮如何得草稿"，核对环节完全一致。

**依赖与风险锚定**：mammoth 仅处理 `.docx`（OOXML），不处理旧 `.doc`；旧格式在导入对话框明确标注"不支持 .doc，请另存为 .docx"。CJS 动态 import 已规避 ESM 冲突；若 M4 实测发现 mammoth 在 ESM 主进程类型声明缺失，补 `@types/mammoth` 或局部 `// @ts-ignore` 声明，不引入额外运行时依赖。

## 八、文档运维工具层（docs-tool）

> 定位：项目自身的确定性文档运维工具层，把"靠 AI 自觉"降为"跑命令有客观结果"——哈希基线、改动体检、需求覆盖矩阵、状态提取、草稿清理，全部可复现、可校验。V 阶段定案（2026-08-06），**代码已落地实现（同日，`scripts/docs-tool.py`）**。本层 `state` 子命令 = 《项目规范.md》G.6 状态文件四要素的生成器；不进产品产物、不影响依赖清单。

### 8.1 定位与目标
- 给 G.6 压缩恢复协议提供 `state` 自动生成器；
- 给单写者铁律提供"改动可追溯"基线（`snapshot` / `diff`）；
- 给监督复核提供客观体检（`matrix` / `check`）；给 G.7 普通任务自检提供半自动化（`selfcheck`，2026-08-07 新增）；
- 零依赖、独立于产品代码（`src/` 未建，不碰 M0–M5）。

### 8.2 目录与运行约定
- 目录：`scripts/`（项目根目录，与 `gen_nav_proto.py` 同级先例一致）；主文件 `scripts/docs-tool.py`。
- 运行：managed Python 绝对路径 `C:/Users/zzh/.workbuddy/binaries/python/versions/3.13.12/python.exe scripts/docs-tool.py <subcommand>`。
- 零依赖：仅 Python 标准库 `hashlib / json / pathlib / re / argparse`（无原生编译 / 无额外二进制 / 无弃坑风险，过 G.2 三问）；**不修改本文档四 依赖清单**。
- 入口：`docs-tool.py` 用 `argparse` 注册 **10 子命令**（snapshot / diff / matrix / check / state / selfcheck / where / brief / clean），统一 `--help`。

### 8.3 10 子命令规格表
| 子命令 | 输入 | 输出 | 算法要点 |
|---|---|---|---|
| **snapshot** | `file/*.md` | `.dev/docs-hashes.json`（相对路径 + SHA-256 + mtime 基线） | 遍历 `file/` 下所有 `.md` 计算哈希；只读取不写 `file/` 内容 |
| **diff** | 基线 + 当前 `file/` | 改动文件清单（新增/修改/删除） | 重算哈希对比基线；无差异输出"0 文件改动" |
| **matrix** | 简报/草稿/正式文档 | 需求覆盖矩阵（需求→落点→状态，标"有需求无落点"） | 扫描 `draft/` 各包简报"合并归属"与正式文档落点交叉核对缺口 |
| **check** | 正式文档 + 草稿 | 体检报告（引用断裂 + 索引完整性 + 术语） | 校验相对文件名引用是否存在（退役资产 ♻ 豁免）、主文档索引是否覆盖新增章节、旧词提示（C1/C4/C6） |
| **state** | `draft/` 自检 + `rubbish/` 复核 + 简报标题 | 状态文件四要素 | 自动提取 `changedFiles`（复用 diff）+ `passedChecks`（读自检/复核）+ `blockers`（待拍板）；`goal` 待 AI 补填或 `--goal-from-briefs` 从 `draft/` 简报自动拼接（空目录回退）；写入 `.dev/G6-state.md` |
| **selfcheck** | `file/` + `project/src/`（只读） | G.7 结构化自检报告（CH1–CH6） | CH1 引用断裂（日志/历史叙述豁免、退役 ♻）/ CH2 索引同步（空格容错）/ CH3 术语统一（C6 复用）/ CH4 硬编码中文（排除 i18n/注释/t()/__tests__，证据=文件:行）/ CH5 日志已登记（当日 `### YYYY-MM-DD`）/ CH6 代码-文档同步（**条件激活**：settings.ts 真核对白名单；resume.ts 未落码则 ♻ 待激活）；**警告非硬失败**，AI 人工裁决 |
| **where** | 关键词（如 F19） | 各文档引用位置清单（文件:行:摘要） | C5 跨文档一致性核对加速器（只读，非自动化判定） |
| **brief** | `--stage --id --topic` | `file/draft/<stage>_<id>_<topic>.md` 简报骨架 | 按《项目规范.md》§三 4 七要素模板生成，只写 `draft/`；已存在则跳过 |
| **clean** | `file/draft/` | 删除草稿（封装） | 合并验收后由组长调用，删前打印待删清单二次确认 |

### 8.4 写权限边界（红线）
- **红线**：`docs-tool.py` **只写 `.dev/` 与 `draft/`**，禁碰 `file/` 正式文档（含《项目日志.md》《项目实现情况.md》《项目功能.md》等）。
- 理由：与 G.6 hooks 写权限红线同一条（写权限只到状态层）——防击穿「单写者铁律」（组长唯一写正式文档）。`snapshot`/`diff`/`matrix`/`check`/`selfcheck`/`where` 只读 `file/`（selfcheck 另只读 `project/src/`）；仅 `state` 写 `.dev/`、`clean` 与 `brief` 写 `draft/`（删/建）。
- 任何子命令不得因"顺手"修改 `file/` 下正式文档；越权即 bug。

### 8.5 与 G.6 的关系
- `state` 子命令 = G.6 状态文件四要素的生成器，字段严格为 `goal` / `changedFiles` / `passedChecks` / `blockers`（同源约束）。
- `snapshot` + `diff` 为 G.6「写入时机」提供客观基线；`matrix` 为 G.6「需求覆盖矩阵」提供自动提取。
- 即使宿主未配 PreCompact hook，AI 也能在会话收尾手动跑 `docs-tool.py state` 刷新状态层（等价降级路径，见 `file/rubbish/宿主hooks实测指引.md`）。

### 8.6 规范化与实现分期
- 规范化：每个子命令函数带 docstring；`--help` 覆盖全部；单一职责（不串联）；失败可诊断（不静默吞异常）。
- **实现状态（2026-08-06 已落地）**：V 阶段落规格，同日由用户指令落地实现为 `scripts/docs-tool.py`（6 子命令全绿）。验收通过（§8.6 标准）：`snapshot`→`diff` 输出"0 文件改动"；改一个文档后再 `diff` 列出该文件；`state` 输出四要素字段名与《项目规范.md》G.6 一致且幂等（同小节覆盖）；`check` 实测揪出并修复 1 处断裂引用（《项目功能.md》引用已删草稿《U1_功能体系主次分层方案.md》→ 改指《项目实现情况.md》§2.2 #26）。
- **扩展实现（2026-08-07 已落地）**：① 新增 `selfcheck`（G.7 半自动化，CH1–CH6，证据输出 + 警告非硬失败，条件激活的代码-文档检查）；② 新增 `where`（C5 核对加速）；③ 新增 `brief`（简报骨架生成）；④ `state` 增 `--goal-from-briefs`；⑤ `check`/`selfcheck` 增退役资产豁免（线框/导航图 2026-08-07 删除，历史引用 ♻ 不误报）。实测全绿：selfcheck 首跑揪出 3 处历史豁免引用 + settings.ts 11 键一致 + resume.ts 条件激活。**沙箱假阳性**：`clean` 的删除在沙箱被 safe-delete shim 拦截（回收站不可用），用户本机正常（G.3 口径）。
